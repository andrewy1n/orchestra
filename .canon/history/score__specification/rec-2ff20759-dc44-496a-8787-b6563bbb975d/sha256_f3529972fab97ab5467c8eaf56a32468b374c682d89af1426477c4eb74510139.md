## Requirements

R1: `SqliteBackend` implements `Backend` and is selected when `config.json` sets `"backend": "sqlite"`.
R2: The DB path is `~/.canon/<repo-name>/canon.db`, resolved through the store binding `global`.
R3: The DB has the tables `ops`, `records`, `revisions` and `meta`.
R4: A trigger rejects every UPDATE and every DELETE on `ops`.
R5: Every write appends its op and updates `records` and `revisions` in one transaction opened with `BEGIN IMMEDIATE`.
R6: A write with a stale `expected_revision` raises `StaleWriteError` and writes nothing.
R7: A `supersede` writes the successor and the predecessor change in one transaction. A failure leaves neither change.
R8: N processes that each write M distinct records leave exactly N×M records and N×M ops.
R9: Two processes that update one record with the same `expected_revision` produce exactly one success and one `StaleWriteError`.
R10: The DB opens with `journal_mode=WAL` and a busy timeout of 10 seconds.
R11: `canon validate` passes on a DB store and fails when a `records` row differs from the fold of its ops.
R12: `canon backup` writes a consistent copy to `~/.canon/<repo-name>/backups/<timestamp>.db` and keeps the 14 newest.
R13: For the same op sequence, the DB backend and the file backend produce the same revision hash for every record.
R14: The existing `tests/canon` suite runs against both backends through one parametrized fixture.

## Acceptance criteria

- R1, R2, R3, R4, R6, R7, R10, R12: unit tests in `tests/canon` against a temporary DB.
- R5, R8, R9: a multiprocess stress test with real `multiprocessing` workers on a temporary DB.
- R11: a test alters a row with raw SQL and asserts `canon validate` fails.
- R13: a test replays one op sequence on both backends and compares hashes.
- R14: the parametrized suite passes for `files` and `sqlite`.

## Constraints

- Python standard library `sqlite3` only. No new dependency.
- `config.json`, `schemas/` and `store-binding.json` stay files in the repo.
- Revision hashing uses the existing `revision.py` for both backends.
- Query filtering (`--where`, `--grep`) keeps its current semantics in `query.py`.

## Non-goals

- Import, export and the real store (phase `importer`).
- Switching this repo to the DB (phase `cutover`).
- Wiring `canon backup` into a hook (phase `cutover`).
- Pushing `--where` filters into SQL.

## Invariants

- No code path updates or deletes an op.
- A `records` row is always the fold of its record's ops.
- A failed write leaves the DB as it was.

## Assumptions

- WAL mode works on the filesystem that holds `~/.canon`. It does not work on network or `/mnt/c` filesystems. This machine keeps the home directory on ext4.
- The store holds fewer than about 100,000 records, so a per-type scan with filtering in Python is fast enough.
