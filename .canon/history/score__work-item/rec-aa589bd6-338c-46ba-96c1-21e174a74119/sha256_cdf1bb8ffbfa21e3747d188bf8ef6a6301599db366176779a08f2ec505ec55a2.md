## Description

Judge claims from `run_tests` outcomes. Confirm a claim that would pass, and report `unstable` when the confirmation disagrees.

## Approach

Work in `/home/andrewyin/affidavit--runner-adapter` on branch `phase/runner-adapter`. Edit `affidavit/verdict.py` and `tests/test_verdict.py`. Do not edit `affidavit/manifest.py`, `affidavit/runner.py`, or `affidavit/oracle_red.py`.

1. Delete `_pytest_at`, `_FAILED_RE`, and the stdout scrape. Stop importing `affidavit.oracle_red`. `affidavit/cli.py` already exits 0 only when `result` is `pass`; leave that line.
2. Keep the detached worktree. For each revision, call `run_tests` with that revision's `Manifest.runner` and the union of pending witness ids. A claim is viable when every base id is `assertion_failed` and every head id is `passed`. Call `run_tests` again in the same worktree for the witnesses of viable claims, then remove the worktree.
3. A second outcome that differs marks each viable claim that lists that id `unstable`, with no `reason`. A claim that is not viable fails `not assertion` when any base id is not `assertion_failed`, and `tests failed` when the base is an assertion red and any head id is not `passed`. The verdict `result` is `fail` when any claim failed, `unstable` when any claim is `unstable` and none failed, and `pass` otherwise.
4. Keep the existing pass, hash-mismatch, and collection-error tests green. Add `test_verdict_ignores_pytest_stdout`, which reads `affidavit/verdict.py` and fails if it contains `_FAILED_RE` or `is_assertion_level_failure`.
5. Add a fixture command in the test repo, named by `runner`, that writes JUnit with `name` set to the witness id. `test_verdict_fixture_junit_pass` is a base failure and a head pass. `test_verdict_fixture_junit_error` is a base error, so the claim is `not assertion`. `test_verdict_fixture_junit_head_failure` fails the head, so the claim is `tests failed`. Add no module under `affidavit/` for that command.
6. `test_verdict_unstable_when_confirmation_disagrees` counts invocations in the worktree: the first base run writes a failure and the second writes a pass, and the head passes both times. The claim result is `unstable` and the process exit is non-zero. `test_verdict_skips_confirmation_on_failed_claim` uses a base error and records one invocation of that id.
