## Architecture

A pure function in `orchestra/score/analyze.py` takes the store's record dicts, a phase slug, and a stage. It returns a list of findings. It does no I/O. `orchestra/cli.py` adds the `analyze` subcommand: it loads records through the existing store access, calls the function, prints text or JSON, and sets the exit code. Three skill files get short instructions: settle-phase (marker), plan-phase (plan-stage gate), execute-phase (close-stage gate).

Record selection for phase P: the active `score:specification` and `score:design` with subject P, non-withdrawn `score:work-item` with `payload.phase` P, and active `score:acceptance` with `payload.phase` P. Check-runs are matched to an acceptance by `criterion_id`, and the latest by `recorded_at` counts.

## Interfaces

- `orchestra analyze <phase-slug> [--stage plan|close] [--json] [--cwd DIR] [--store DIR]`. Exit 0 no errors, 1 errors, 2 usage or store failure. `--cwd` and `--store` follow `review-brief`.
- `analyze_phase(records, phase, stage) -> list[Finding]`. `Finding` has `severity` (`error` or `warning`), `code`, `subject`, and `message`.
- Finding codes: `spec-id-not-in-body`, `body-id-not-in-spec`, `requirement-no-work-item`, `requirement-no-acceptance`, `work-item-unknown-requirement`, `acceptance-unknown-requirement`, `clarification-marker`, `compound-requirement`, `acceptance-no-check-run`, `acceptance-not-passing`.
- Marker: `[NEEDS CLARIFICATION: <question>]`. The check matches the prefix `[NEEDS CLARIFICATION` outside inline code spans, so documents can quote the marker.

## Decisions

- `analyze-gate-strength`: skill gates at plan review and phase close.
- `marker-scope`: the marker is an error in the specification and the design.
- `analyze-stage-flag`: an explicit `--stage plan|close` flag.

## Invariants

- No write to the store or the disk.
- Exit 1 if and only if an error finding exists.
- Same store and arguments give the same output.
- `orchestra/score/` imports only `canon`.

## Assumptions

- Requirement lines are `Rn: <text>` and one per line.
- `criterion_id` is the acceptance record id.
- One active specification and one active design per phase.

## Tradeoffs

- Skill gates are cheap and consistent with `## Proof`, but an agent can skip them.
- Body parsing is line and regex based. It is simple and fails visibly on a malformed line, but it does not understand markdown.
- The compound-requirement check is a heuristic, so it is a warning.

## Risks

- A superseded acceptance gets a new id, so its old check-runs no longer match. At close this correctly reports a missing check-run, but it can surprise the agent. The finding message names the acceptance id.
- The `and` heuristic can warn on legitimate single behaviors. Warnings never change the exit code.
- Skill text drifts from the command. Scanner tests pin the command line and stage names in each skill.
