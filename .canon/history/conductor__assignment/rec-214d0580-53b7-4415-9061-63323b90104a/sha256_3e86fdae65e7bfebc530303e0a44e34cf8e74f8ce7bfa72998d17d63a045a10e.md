## Orientation

Work only in `/home/andrewyin/affidavit--claims-manifest` on branch `phase/claims-manifest`. The primary checkout `/home/andrewyin/affidavit` stays on `main` and is not yours. No other executor is writing this worktree. Commit only your files, and exclude `.artifacts`:

```
git add affidavit/verdict.py affidavit/cli.py tests/test_verdict.py
git commit -m "verdict-command"
```

Do not edit `.artifacts`. Do not call `adaptive-artifacts`. Import `affidavit.manifest` and `affidavit.amendment`. Do not change their behavior. Do not edit `affidavit/oracle_red.py` except to call `is_assertion_level_failure`.

`load_manifest` returns a `Manifest` whose `claims` are `Claim` objects (`id`, `text`, `tests`, `oracle_hashes`). `authorize` takes mappings with `id`, `tests`, and `oracle_hashes`, plus amendment dicts and the two allowlist blobs. `resolve_commit`, `merge_base`, `load_allowlist`, and `hash_oracle_files` are in `affidavit.manifest`.

The real entry point is `bin/aff` in this worktree. Tests invoke that binary as a subprocess.

### Requirements

R1: A manifest committed in the work repo is the authority for each claim's id, text, oracle test ids, and oracle file hashes. `aff verdict` computes its result from that manifest and from re-executing the tests. It does not read the adaptive-artifacts store. A `project:check-run` in that store, including one with `runner: aff` and `result: pass`, does not change the verdict.

R2: `aff verdict` re-executes the named claims' frozen oracle tests at `--at`, and re-executes them at `--base` in a temporary worktree. It exits 0 only when, for every named claim, the oracle file bytes at that revision match the manifest hashes, the tests fail at `--base` on an assertion, and the tests pass at `--at`. An import error, collection error, or syntax error at `--base` is not a passing red.

R3: When a claim's test ids or oracle hashes differ between the manifest at `--base` and the manifest at `--at`, the `--at` manifest must contain an amendment entry that connects those two states and whose signature verifies under the allowlist committed at `--base`. The allowlist at `--at` must be byte-identical to the allowlist at `--base`. A hash change with no amendment, a signature that does not verify, a signature under a key absent from the base allowlist, or an allowlist that changed between the two revisions fails the verdict.

R4: The behavior in R1–R3 is locked by tests that invoke the `aff verdict` CLI as a subprocess. Those tests include a `--cwd` that is a phase worktree other than the store checkout, and a case where a forged stored check-run leaves the verdict unchanged.

### Invariants

- Verdict inputs are the git objects at `--base` and `--at` plus the processes those checkouts run.
- An amendment verifies only against the allowlist blob at `--base`.
- Allowlist bytes at `--at` equal allowlist bytes at `--base` whenever the command accepts a hash or test-id change.
- Oracle file bytes at a revision hash to the `oracle_hashes` on that revision's claim.
- A base result counts only when `is_assertion_level_failure` is true for the pytest output.

### Assumptions

- `main` exists when `--base` is omitted, and `--at` is a descendant of the oracle-freeze commit.
- The signing key that matches `.affidavit/allowed_signers` is available to the owner and is not loaded in the agent session. This phase checks signatures; it does not provision keys.
- Temporary worktrees can be created from `--cwd` and removed after the run.
- Pytest is the runner for every claim in this phase.

### Decisions

- claims-authority: a committed manifest in the work repo holds claims, oracle test ids and hashes, and approved amendments; the store is only a log
- verdict-authority: aff verdict re-executes frozen oracle tests at the revision (and base in a temporary worktree); stored runs are an audit log and cache
- amendment-approval: an amendment entry in the committed manifest verifies under a key in the allowlist committed at base
