## Architecture

A small builder (shell script or Python under `tests/fixtures/` / `scripts/`) materializes `tests/fixtures/verdict-repo` as a fresh git repo from tracked templates: green `app.py`, oracle test, `.affidavit/manifest.json` for `claim-widget`, and any runner support the verdict path needs. The GitHub workflow calls that builder in a step before `Run aff verdict`. Attest emit/verify steps stay as they are.

## Interfaces

- Builder: idempotent or clean-slate; writes under `tests/fixtures/verdict-repo`; exits non-zero on failure; prints nothing the later steps depend on beyond the directory existing as a git repo.
- Workflow step: `Build verdict fixture` (name flexible) runs the builder; existing steps keep `--cwd` / `fixture_cwd` defaults.
- Pytest R4: reads workflow YAML for a fixture-build invocation and asserts template/builder paths exist on disk.

## Decisions

- `ci-fixture-supply`: CI setup builds git repo from tracked templates under `tests/fixtures/verdict-repo`.

## Invariants

- No committed nested `.git` in the fixture path.
- Claim id default `claim-widget` unchanged.

## Assumptions

- Minimal green subject matching unit-test shape (`value == 1`) is enough for attest CI.
- Sharing logic with pytest helpers is optional; duplication of a tiny tree is acceptable for S-size repair.

## Tradeoffs

- Templates + builder vs inline YAML: builder is reviewable and locally runnable; costs one extra file.
- Strengthening R4 pytest may break the old string-only acceptance until templates land in the same change.

## Risks

- Template/manifest drift from what `aff verdict` currently requires (runner fields, freeze hashes) — mitigate by running the builder + verdict once in the phase verify command.
- Missing GitHub secrets still fail later steps even when the fixture builds; that is out of scope but should not be misread as a fixture bug.
