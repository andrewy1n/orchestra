## Architecture

- `scripts/wheel_smoke.py` is a standard-library script. It takes an optional `--wheel PATH`.
- Without `--wheel`, it copies the tracked files (`git ls-files`) into a temporary directory and runs `uv build --wheel` there. The checkout gets no `build/` or `*.egg-info`, and ignored files such as `node_modules` cannot enter the wheel.
- It creates a venv with `uv venv` in a temporary directory and installs the wheel with `uv pip install`.
- It runs every check with the venv interpreter and console scripts, from a temporary working directory outside the checkout. The checks are: `orchestra --help`; `canon --help`; in a temporary git repository, `canon init --schemas score,conductor,tuner` then `canon validate`; `orchestra install --list` with `claude` in the output; and imports of `dashboard`, `dashboard.web`, `installer`, `installer.adapters`.
- The script prints each check name and result, then exits 1 if any check fails. It runs all checks before it exits.
- `ci.yml` gains a `wheel` job: checkout, `astral-sh/setup-uv@v6` on Python 3.10, then `python3 scripts/wheel_smoke.py`. It needs no `uv sync`, because the script installs into its own venv.
- `tests/test_wheel_smoke.py` builds one wheel, runs the script with `--wheel`, and checks that the checkout is unchanged. A second case removes `installer/providers.json` from a copy of the wheel and expects a non-zero exit.
- `tests/test_ci_workflow.py` gains tests that the `wheel` job exists, is blocking, and runs the script.
- `README.md` names `python3 scripts/wheel_smoke.py` next to the other local checks.

## Interfaces

- Local and CI command: `python3 scripts/wheel_smoke.py [--wheel PATH]`. Exit 0 means every check passed.
- The `wheel` job name is the interface to `repo-hygiene`, which can list it as a required check.
- The check list in the script is the one source for the wheel's expected installed behavior.

## Invariants

- Every other blocking job in `ci.yml` is still blocking.
- No check runs with the checkout as the working directory or on `sys.path`.
- The wheel is built from tracked files only.
- The script leaves the checkout unchanged.

## Assumptions

- `ci-workflow` and `wheel-contents` have merged, and `mypy-gate` has merged before execution starts.
- `uv build --wheel`, `uv venv`, and `uv pip install` work on the runner after `setup-uv`.
- Today every check passes against a wheel built from the checkout.

## Tradeoffs

- A script buys checks that `--help` cannot make, and one command for local and CI runs. It costs a file to maintain and a test that pins it.
- Building from a tracked-file copy buys a wheel that matches a clean checkout. It costs a copy step and a `git` dependency in the script.
- The script repeats part of `tests/test_wheel_contents.py`. The test checks an editable and a wheel install in-process. The script checks the installed console scripts.

## Risks

- The check list drifts from the real CLI. A renamed schema set or host breaks the script and not the product. The test run in `test-orchestra` catches this first.
- The web dashboard cannot start from the installed wheel, and this phase does not check it. The backlog idea covers it.
- `mypy-gate` and this phase both edit `ci.yml` and `tests/test_ci_workflow.py`. Merge `main` and re-run before the final merge.
- A runner without `git` or `uv` on `PATH` fails the script. GitHub's `ubuntu-latest` has both after `setup-uv`.
