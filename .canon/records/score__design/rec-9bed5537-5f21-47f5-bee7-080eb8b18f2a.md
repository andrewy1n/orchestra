## Architecture

A new loader `areas.py` in `dashboard/backend` reads `composer:area` and `composer:idea` records through `store.py`, groups ideas by `payload.area`, and returns area views. A Pydantic model and a route expose them at `/api/areas`. The UI adds a state module, an Areas section on Home, and an area detail screen.

## Interfaces

- `GET /api/areas` returns a list of areas, each with `subject`, `title`, `scope`, `open_count`, and `ideas`.
- Each idea carries `subject`, `text`, `status`, `area`, `effort`, and `phase`.
- Route: `#/area/<subject>`, in the same style as the existing routes.

## Decisions

- `idea-both-fields`: show an idea in both places.
- `area-idea-states`: open and promoted.
- `area-view-read-only`: read-only first.

## Invariants

- The effort backlog output is the same as before.
- The area loader reads only through `store.py`.

## Assumptions

- The snapshot types list in the loader can add `composer:area` without breaking foreign stores. The soft-type handling covers a store without that type.

## Tradeoffs

- An idea counts in two views, so counts may add up to more than the idea total.

## Risks

- The area text is long markdown and slows the response. Mitigation: return the scope text only on the area detail route if the payload is large.
