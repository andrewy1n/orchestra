## Architecture

`orchestra/canon/transfer.py` holds `export_ops(backend, out)` and `import_ops(backend, src)`. Export iterates record types and ids in sorted order and calls `read_ops` for each chain. It writes `{"record_type": ..., "record_id": ..., "seq": ..., "op": {...}}` with sorted keys and no export-time fields. The same ordering makes two exports byte-identical.

Import opens one `transaction()` on an empty backend. For each line it appends the op at its seq, then folds the chain with the existing `fold` and writes the `records` row and one `revisions` row per op that changes state. It compares the folded revision with the revision stored in the last op, and aborts the whole transaction on a gap, a duplicate seq or a mismatch, naming the record.

`scripts/verify_import.py` imports a file store into a scratch DB, then walks `records/` and `history/` of the source and compares each file's revision to the DB. It prints `<n> records, <m> mismatches` and exits non-zero when `m` is above zero.

## Interfaces

- `canon export --out FILE [--store PATH]`
- `canon import FILE [--store PATH]`
- `export_ops(backend: Backend, out: TextIO) -> int`
- `import_ops(backend: Backend, src: TextIO) -> int`
- `scripts/verify_import.py SOURCE_STORE`

none

## Invariants

Ops are never rewritten on import. Export order is a total order on (record type, record id, seq). Import is atomic.

## Assumptions

- A checkpoint op carries enough state for `fold` to start there.
- `history/` holds one file per revision that `revisions` must reproduce.

## Tradeoffs

JSONL of ops is larger than a dump of final records. It keeps full history, so the DB can be rebuilt exactly and the round-trip proof can compare revisions.

## Risks

- A real chain has a case the unit tests do not cover. `verify_import.py` runs on the real store, so such a case shows up there.
- The store changes between the verify run and the cutover. The cutover re-runs verify just before the switch.
