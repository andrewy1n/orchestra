## Architecture

Two evidence planes stay separate:

1. **Orchestra check-runs** — operational proof that `orchestra check` / `orchestra suite` ran a `verify_command` or suite command. Stamped `runner: "orchestra"`. close-batch uses them for red-first and result matching.
2. **Affidavit claims** — manifest claims earned only via Affidavit verbs (`verdict`, observation/`bind`/`recheck`, `attest` where used). close-batch additionally requires `aff verdict` and `aff recheck` success when the acceptance names a manifest claim.

Orchestra never imports Affidavit. It shells out to `aff` on PATH. Assertion-level red uses a new or extended Affidavit CLI verb that wraps today's `oracle_red` logic; until that verb exists, oracle-backed close refuses.

## Interfaces

- `orchestra check` / suite record: set `RUNNER = "orchestra"` (constant shared by check and suite).
- `orchestra close-batch`: `RUNNER_MARKER = "orchestra"`; refuse `aff`.
- Manifest-claim close gate: subprocess `aff verdict --cwd … --at <revision> <claim-id>` and `aff recheck --cwd … --claim <claim-id>`; non-zero → `CloseRefused`.
- Assertion-level red: subprocess to Affidavit CLI (exact subcommand fixed at implement time; preferred shape: stdin or file of check-run JSON → exit 0 if assertion-level). No `sys.path` checkout probe.
- Skills: remove hand-typed `runner: "aff"` examples; suite path uses `orchestra suite record` only.

## Decisions

- `evidence-authority-approach`: honest stamp + Affidavit claim gate (not attest-seal, not skills-only).
- `runner-marker`: stamp string `orchestra`.
- `claim-gate-verbs`: engine enforces both `aff verdict` and `aff recheck` for manifest-backed acceptances.
- `legacy-runner-stamp`: refuse `aff` (no grandfather).
- `oracle-red-surface`: Affidavit CLI only; no Python import from Orchestra.

## Invariants

- A typed-in check-run with `runner: "orchestra"` remains forgeable as an Orchestra operational record; Affidavit claim earning does not trust that stamp.
- Manifest claim `done` requires Affidavit CLI success, independent of the check-run stamp.
- Import direction: Orchestra → Affidavit CLI only; Affidavit does not import Orchestra.

## Assumptions

- Claim id on an acceptance (or equivalent link skills already document) is available to close-batch for the manifest gate.
- Affidavit CLI addition for assertion-level red can land in the Affidavit repo as part of this phase's delivery when Orchestra Landing needs it.

## Tradeoffs

- Clean break on `runner: "aff"` forces re-runs for in-flight closes; avoids dual-marker ambiguity.
- Dual gate (verdict + recheck) is stricter and matches existing skill prose; slightly more process at close.
- CLI-only oracle_red adds a small Affidavit surface instead of keeping a path workaround.

## Risks

- Affidavit CLI gap blocks oracle-backed closes until the verb ships — mitigate by sequencing Affidavit CLI before flipping the import removal, or refuse with an explicit message.
- Detecting "acceptance names a manifest claim" incorrectly could skip or over-apply the gate — pin detection rules in plan-phase tasks and tests.
- Hand-authored `runner: "orchestra"` can still fake operational check-runs; out of scope (Affidavit plane is the hard gate for claims).
