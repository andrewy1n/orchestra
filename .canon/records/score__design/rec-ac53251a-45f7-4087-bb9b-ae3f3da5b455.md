## Architecture

`orchestra/canon/sqlite_backend.py` implements `Backend`. One DB file holds:

- `ops(record_id, seq, op_json, PRIMARY KEY (record_id, seq))`, append-only, with `BEFORE UPDATE` and `BEFORE DELETE` triggers that `RAISE(ABORT)`.
- `records(record_id PRIMARY KEY, record_type, subject, lifecycle_state, revision, recorded_at, payload_json, body, relationships_json)`, with indexes on `(record_type, subject)` and `(record_type, lifecycle_state)`.
- `revisions(record_id, revision, record_json, PRIMARY KEY (record_id, revision))`, replacing the `history/` snapshots.
- `meta(key, value)` for the format version.

`transaction()` opens a connection with `isolation_level=None`, runs `BEGIN IMMEDIATE`, and commits or rolls back on exit. Inside one transaction a write reads the chain, decides accept or reject with the existing `_decide_write` logic, appends the op, and upserts `records` and `revisions`. The `expected_revision` check happens inside the transaction, so the check and the write cannot be split by another writer. The connection sets `journal_mode=WAL`, `synchronous=NORMAL` and `busy_timeout=10000`.

Reads use the `records` table: `read_record` by id, `iter_records(type)` by type. Filtering stays in `query.py`. No fold runs at read time. The fold remains for `check_integrity` and the importer.

The DB path comes from the store binding. `global` resolves to `~/.canon/<repo-name>/`, and the backend opens `canon.db` there. Config and schemas still load from `<repo>/.canon/`, so `Project` holds a config root and a data root. `canon backup` calls `sqlite3.Connection.backup` into `backups/` and prunes to 14 files.

## Interfaces

- `SqliteBackend(config_root: Path, data_root: Path)` implements `Backend`
- `canon backup [--keep N]`
- `meta` key `format` = `canon-sqlite/1`
- Store config key `"backend": "sqlite"`

## Decisions

canon-store-engine, canon-store-topology, canon-db-location, canon-config-in-git, canon-backup-command.

## Invariants

Ops are never updated or deleted. Each write is one transaction. The revision of a record is computed by `revision.py` from the same content as in the file backend.

## Assumptions

- WAL works on the filesystem under `~/.canon`.
- Python's bundled SQLite supports WAL, triggers and the online backup API.

## Tradeoffs

Filtering in Python keeps query semantics identical to the file store, at the cost of reading every row of a type. Storing JSON in columns instead of normalized tables keeps the schema stable as record types change.

## Risks

- A disk loss loses the store between backups. The backup command and the 24-hour hook limit the loss.
- A long-running reader blocks WAL checkpoints. Readers here are short-lived commands.
- A writer holds the lock longer than the busy timeout under heavy load. The stress test sets the limit.
- A split between the config root and the data root can send a worktree to the wrong DB. R2 and the cutover worktree test cover it.
