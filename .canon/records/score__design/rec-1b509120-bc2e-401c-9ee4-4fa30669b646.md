## Architecture

Verdict runs witnesses through one primitive, `run_tests`, selected by `runner-template`, classified by `assertion-signal`, and confirmed by `unstable-rerun`. The template stays unsigned until `frozen-environment` (`runner-template-freeze`).

1. `manifest.py` parses an optional `runner`. Absent means the shipped pytest argv. Present must be a non-empty list of non-empty strings containing an element `{tests}` and an element that contains `{report}`. Any other shape raises `ManifestError`. `Manifest` gains a `runner` field. Each revision uses the runner loaded from that revision.
2. `affidavit/runner.py` provides `run_tests(worktree, test_ids, runner)`. It expands `{tests}` into one argument per id and substitutes `{report}` with a temporary XML path. It starts the process from that argument list, in the worktree, with `PYTHONPATH` and `PYTEST_ADDOPTS` removed. It parses the JUnit file and returns one outcome per requested id. A missing report, or an id with no matching case, is `not_run`.
3. A case matches an id when `name` equals the id. Otherwise, when `file` is present, the id is `file`, then any classname segments after the dotted stem of `file`, then `name`, joined with `::`. Two cases for one id collapse to `errored` when any of them is an error, and to `assertion_failed` when any remaining case is a failure.
4. `verdict.py` creates the detached worktree as it does today and calls `run_tests` with the union of pending witness ids. It then calls `run_tests` again in that same worktree for the confirmation ids, and removes the worktree afterward. It no longer reads pytest stdout and no longer calls `is_assertion_level_failure`.
5. A claim is viable when every base id is `assertion_failed` and every head id is `passed`. Confirmation ids are the witnesses of viable claims. A second outcome that differs marks each viable claim that lists that id `unstable`. A claim that is not viable fails with `not assertion` when any base id is not `assertion_failed`, and with `tests failed` when the base is an assertion red and any head id is not `passed`.
6. The verdict result is `fail` when any claim failed, `unstable` when any claim is `unstable` and none failed, and `pass` otherwise. Tests keep the current pytest fixtures on the default runner, add a fixture command that writes JUnit for pass, error, and failure, and add a fixture whose first base run is `assertion_failed` and whose confirmation run is `passed`.

## Interfaces

- `Manifest.runner: tuple[str, ...]`
- Shipped default: `python3 -m pytest -o junit_family=xunit1 {tests} --junitxml={report}`
- `run_tests(worktree: Path, test_ids: Sequence[str], runner: Sequence[str]) -> dict[str, str]`
- Outcome strings: `passed`, `assertion_failed`, `errored`, `not_run`
- Verdict JSON keeps `pass` and `fail` claims. Fail claims keep their `reason`. An unstable claim is `{"id", "result": "unstable"}` with no `reason`. Top-level `result` is `pass`, `fail`, or `unstable`. Exit 0 only when `result` is `pass`.
- `{tests}` is one argv element and expands in place. `{report}` is substituted inside an element. The command is an argument list.

## Decisions

- `runner-template`: the manifest holds an argv template and the report is JUnit XML. An absent `runner` is the shipped pytest template.
- `assertion-signal`: `<failure>` is `assertion_failed`, `<error>` is `errored`, and skipped or absent is `not_run`.
- `unstable-rerun`: one confirmation run of the witnesses that would pass the claim. Disagreement is `unstable`.
- `runner-template-freeze`: this phase does not hash `runner`. `frozen-environment` does.

## Invariants

- Exit 0 only when the verdict result is `pass`.
- Verdict does not read the artifact store.
- Base uses the runner at base. Head uses the runner at head.
- The test process environment has no `PYTHONPATH` and no `PYTEST_ADDOPTS`.
- `affidavit.oracle_red` stays, and its results stay, for orchestra's close path.

## Assumptions

- Pytest's default `junit_family` is `xunit2`. The shipped template sets `xunit1` so `file` is emitted.
- A collection or setup error is `<error>`. A test-body exception is `<failure>`.
- One runner list per manifest is enough until `evidence-kind`.
- The confirmation run shares the first run's worktree.

## Tradeoffs

- A test-body `ModuleNotFoundError` becomes an assertion red, because pytest records it as `<failure>`. Collection errors stay `not assertion`. Orchestra's close path still rejects the in-test import through `oracle_red`.
- The runner list is unsigned until `frozen-environment`. A revision can name a command that writes a passing report.
- Confirmation adds one extra run at each revision that has a viable claim. Claims that already fail do not pay for it.
- A custom runner can put the witness id in `name` and omit `file`. The shipped pytest template relies on `file` plus classname.

## Risks

- A pytest config that still emits `xunit2` drops `file`. Reconstruction then fails and every id is `not_run`, so a claim fails `not assertion` or `tests failed`.
- A runner that exits 0 and writes no report yields `not_run` for every id.
- Two viable claims that share an id share one confirmation outcome.
- A flake whose first run already fails the claim stays `fail`. The confirmation run only demotes a claim that would have passed.
