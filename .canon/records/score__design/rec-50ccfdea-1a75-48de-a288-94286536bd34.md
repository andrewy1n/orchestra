## Architecture

`orchestra.canon.git_backend` grows one runner, `run_git(cwd, *args, **subprocess_kwargs)`, and the existing `git_root`. Every `subprocess` call whose argv starts with `git` under `orchestra/` and `dashboard/` goes through that runner. Callers keep the argv and the decision about errors. `dashboard.landing` still returns `None` on failure. `check.git_head` still raises. Domain commands stay at the call site: tuner worktrees, reviewer diffs, `close_batch` merge-base, validation's name-status diff, and `dashboard.commit`'s `git show`.

`orchestra.canon` defines `record_payload(record) -> dict`. A non-dict payload returns `{}`. `orchestra.views`, `orchestra.conductor.close_batch`, `dashboard.model`, and `dashboard.approval` call it and delete their local getters. Other `_payload` helpers that build a claim or a verdict body stay where they are.

`parse_failing_node_ids` and the output hash stay in `orchestra.conductor.check`. `orchestra.conductor.suite` imports them and deletes its copies, including its copy of the body tail when that tail only exists to serve the hash.

`orchestra.tuner.sign` is the only module under `orchestra/tuner/` that starts `ssh-keygen`. It offers sign and verify, taking the namespace and the payload bytes. `amendment`, `attestation`, and `human_claim` call it and keep their canonical payload text.

`dashboard.web.routes` holds the eleven API routes: method, path, reader method, and query keys. `dashboard.web.service` and `dashboard.web.app` dispatch through that table. The static `/` mount and each server's error mapping stay in that server.

## Interfaces

- `orchestra.canon.git_backend.run_git` and `git_root`.
- `orchestra.canon.record_payload`.
- `orchestra.conductor.check.parse_failing_node_ids` and the output hash.
- `orchestra.tuner.sign` sign and verify.
- The route table in `dashboard.web.routes`, consumed by the stdlib handler and `create_app`.

## Decisions

- `helper-owning-component`: git and payload in canon, the failing-node parser in `conductor.check`, ssh-keygen in tuner, one dashboard route table. Callers keep their failure behavior.

## Invariants

- Canon imports no other orchestra component.
- Tuner does not import conductor.
- Landing's failure result stays `None`. `git_head`'s failure result stays an exception.
- The API path set does not change.

## Assumptions

- A thin runner can pass through the timeout, input, and check flags the current call sites use.
- `wheel-contents` has made `dashboard` importable from the install.

## Tradeoffs

- Every git call site changes, including tuner worktree commands that were not byte-identical copies. The runner is the single place a `git` argv is built. Call sites that need a special error policy stay responsible for it.
- One payload function picks `{}` for a non-dict. Callers that treated only a missing payload as `{}` now share that rule.

## Risks

- A runner that drops `timeout` or stdin changes landing or a tuner git call without a failing unit test. The landing `None` test and the tuner git tests have to cover the kwargs they rely on.
- Suite and check can drift again if suite imports the parser but keeps a private hash. The scan for a second definition is the guard.
