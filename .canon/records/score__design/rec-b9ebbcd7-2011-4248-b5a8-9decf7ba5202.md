## Architecture

Landing still creates `phase/<phase-slug>` and `<repo>/.worktrees/<phase-slug>` once. At the start of each wave, for every task except the verification task, execute-phase creates `task/<phase-slug>/<task-slug>` at that phase tip and adds `<repo>/.worktrees/<phase-slug>--<task-slug>` on it. The executor writes and commits only there. verify-work uses that worktree, and the check-run revision is that commit. At wave end, in the phase worktree, the parent merges passing task branches in task-slug order with `git merge` (fast-forward when git can, merge commit otherwise, never rebase). Failed task branches stay unmerged. A conflict aborts that merge, leaves markers, opens a blocking continuity question, and holds the next wave. Re-dispatch reuses the task branch and worktree and merges the phase tip into the task branch when the tip is not already contained. The verification task runs in the phase worktree after those merges and does not commit. Phase close still commits the phase worktree, merges `phase/<phase-slug>` into `main`, and commits the store on the primary checkout, then removes this phase's task worktrees and deletes task branches contained in the phase branch.

`skills/execute-phase/SKILL.md` carries dispatch, the task-worktree commit, verify cwd, wave-end merge, retry, and the conflict stop. `skills/execute-phase/references/phase-end.md` keeps the phase-close commit on the phase worktree and adds task-worktree removal plus deletion of merged task branches. `tests/test_task_commit.py` locks the per-task path, the passing SHA, merge-after-pass, the conflict stop, the verification exception, and the no-Landing skip. `tests/test_execute_landing.py` stays green, including store writes on the primary checkout.

## Interfaces

- Task branch: `task/<phase-slug>/<task-slug>`, created from `phase/<phase-slug>` at wave start.
- Task worktree: `<repo>/.worktrees/<phase-slug>--<task-slug>`.
- Per-task commit, in the task worktree: `git add -A -- . ':!.artifacts'`, then a conventional commit whose body names the task slug. Skip when there is nothing to commit.
- verify-work `--cwd` is the task worktree. The check-run `revision` is that commit.
- Wave-end merge, in the phase worktree, task-slug order: `git merge task/<phase-slug>/<task-slug>`.
- Retry update, in the task worktree: `git merge phase/<phase-slug>` when the phase tip is not an ancestor.
- Conflict: blocking `project:continuity-question`, subject the effort, scope `merge:<task-slug>`. No marker edits.
- Assignment orientation: the task worktree path is the write root. It does not forbid `git add -A`.
- Phase close: remove each `<repo>/.worktrees/<phase-slug>--<task-slug>` and delete each `task/<phase-slug>/<task-slug>` contained in the phase branch.

## Decisions

task-worktree: one branch and worktree per non-verification task, verify there, merge passing branches at wave end.
task-commit-evidence: the passing SHA is the task-branch commit, merged into the phase branch only after the check passes.

## Invariants

- The passing SHA stays a commit on the task branch and is reachable from the phase branch after a clean merge.
- A failed check does not add that task's commits to the phase branch.
- Task worktrees sit beside the phase worktree, not inside it.
- The parent does not rebase a task branch and does not edit conflict markers.
- `.artifacts` is written only on the primary checkout and is excluded from task and phase commits.

## Assumptions

- Sibling tasks in a wave do not need each other's edits to pass their own checks.
- The verification task plus the phase-end suite see the integrated phase branch.
- Task slugs are unique in the phase and safe as one path segment.
- `.worktrees/` stays gitignored.

## Tradeoffs

Every non-verification task pays for a worktree and a merge, including a wave of one. The phase branch is no longer a single linear series of task commits when two passing branches diverge. Merge conflicts stop the next wave instead of being solved in the prompt.

## Risks

A merge can be textually clean and still fail once both diffs are combined. That shows up on the verification task or the phase-end suite, not on the isolated check-run. A conflict holds the wave until a person answers. Task worktrees use disk until phase close. `tests/test_task_commit.py` currently expects the commit on the phase worktree and a fixed snippet count, so those assertions have to move with the skill text.
