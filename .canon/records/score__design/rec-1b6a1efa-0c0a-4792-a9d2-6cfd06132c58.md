## Architecture

`store.py` reads records with `Project.list` and filters by state and payload in typed functions. The loaders (`snapshot.py`, `task.py`, `phase.py`, `journal.py`) take records and return view types. Shared helpers sit in `records.py`. The write actions stay in the backend modules. One FastAPI app in `server/` maps loader output to Pydantic models. A script dumps the OpenAPI schema, and `openapi-typescript` writes `api-types.ts` into the UI.

## Interfaces

- `store.py` exposes typed read functions and the change token.
- Each loader exposes `load_*` functions as `model.py` does today.
- `server/` exposes the same `/api/*` routes as today.
- A script writes the OpenAPI schema to a file. A check mode compares it with the committed types.

## Decisions

- `typed-store-reads`: typed filters in `store.py`.
- `loader-module-cut`: one module per loader.
- `api-types-codegen`: committed generated types and a CI sync check.
- `one-fastapi-server`: delete the stdlib server.

## Invariants

- Endpoint JSON shapes do not change.
- Only `store.py` reads the store.

## Assumptions

- The Pydantic models can reproduce today's JSON, including optional fields.
- The Python CI job can run `npm`-free generation of the schema and compare it.

## Tradeoffs

- Dashboard-side filtering duplicates a little canon query logic. Canon stays untouched.
- A committed generated file adds a sync check.

## Risks

- A Pydantic model changes a field's JSON shape. Mitigation: the characterization test in R11.
- The loader split exposes a circular import. Mitigation: shared helpers go to `records.py`, and imports point one way.
