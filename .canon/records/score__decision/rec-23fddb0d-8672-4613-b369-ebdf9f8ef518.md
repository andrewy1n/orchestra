## Rationale

`installer/paths.py` takes the payload root as the parent of the `installer` package. That parent is the repo root while `installer/` sits beside `skills/`, `agents/`, and `hosts/`, which are the files `orchestra install` copies. `dashboard/bin/dashboard` puts the repo root on `sys.path` and runs `dashboard/__main__.py`. The app and its tests import `dashboard`, and the product CLI does not. Listing both packages in the orchestra wheel makes those imports succeed from an editable install. The supported install is `uv tool install --editable`.

## Counter-argument

Moving them to `orchestra.dashboard` and `orchestra.stage.installer` would put every component under `orchestra.*`, which is what the monorepo plan names, and `tests/test_boundaries.py` would then see their imports. The installer would have to stop resolving its payload as the parent of the package, because that parent would be `orchestra/stage` in a checkout and `site-packages` in a wheel.
