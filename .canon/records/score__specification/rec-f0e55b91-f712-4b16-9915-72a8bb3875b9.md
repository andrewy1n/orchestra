## Requirements

R1: `SqliteBackend` implements `Backend`.
R2: A store config with `"backend": "sqlite"` selects `SqliteBackend`.
R3: The DB path is `~/.canon/<repo-name>/canon.db` under the store binding `global`.
R4: The DB has these tables: `ops`, `records`, `revisions`, `meta`.
R5: A trigger rejects every UPDATE on `ops`.
R6: A trigger rejects every DELETE on `ops`.
R7: Every write changes `ops`, `records`, `revisions` in one transaction opened with `BEGIN IMMEDIATE`.
R8: A write with a stale `expected_revision` raises `StaleWriteError`.
R9: A rejected write leaves the DB unchanged.
R10: A failed `supersede` leaves neither the successor nor the predecessor change.
R11: N processes that each write M distinct records leave N×M records in the DB.
R12: Each record written by those processes has exactly one op.
R13: Of two processes that update one record with the same `expected_revision`, exactly one succeeds.
R14: The DB opens with `journal_mode=WAL`.
R15: The DB connection sets a busy timeout of 10 seconds.
R16: `canon validate` passes on a valid DB store.
R17: `canon validate` fails when a `records` row differs from the fold of its ops.
R18: `canon backup` writes a consistent copy of the DB to `~/.canon/<repo-name>/backups/<timestamp>.db`.
R19: `canon backup` keeps the 14 newest copies.
R20: For the same op sequence, both backends give every record the same revision hash.
R21: The `tests/canon` suite runs against both backends through one parametrized fixture.

## Acceptance criteria

- R1, R2, R3, R4, R5, R6, R8, R9, R10, R14, R15, R18, R19: unit tests in `tests/canon` against a temporary DB.
- R7, R11, R12, R13: a multiprocess stress test with real `multiprocessing` workers on a temporary DB.
- R16: `canon validate` on a temporary DB store exits 0.
- R17: a test alters a row with raw SQL and asserts `canon validate` fails.
- R20: a test replays one op sequence on both backends and compares hashes.
- R21: the parametrized suite passes for `files` and `sqlite`.

## Constraints

- Python standard library `sqlite3` only. No new dependency.
- `config.json`, `schemas/` and `store-binding.json` stay files in the repo.
- Revision hashing uses the existing `revision.py` for both backends.
- Query filtering (`--where`, `--grep`) keeps its current semantics in `query.py`.

## Non-goals

- Import, export and the real store (phase `importer`).
- Switching this repo to the DB (phase `cutover`).
- Wiring `canon backup` into a hook (phase `cutover`).
- Pushing `--where` filters into SQL.

## Invariants

- No code path updates or deletes an op.
- A `records` row is always the fold of its record's ops.
- A failed write leaves the DB as it was.

## Assumptions

- WAL mode works on the filesystem that holds `~/.canon`. It does not work on network or `/mnt/c` filesystems. This machine keeps the home directory on ext4.
- The store holds fewer than about 100,000 records, so a per-type scan with filtering in Python is fast enough.
