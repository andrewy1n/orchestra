## Requirements

R1: `orchestra check` writes each `project:check-run` with `payload.runner` equal to the string `orchestra`.
R2: The suite check-run writer used by `orchestra suite record` writes `payload.runner` equal to the string `orchestra`.
R3: `orchestra close-batch` treats a stored check-run as runner-produced only when `payload.runner` equals `orchestra`.
R4: `orchestra close-batch` refuses a stored check-run whose `payload.runner` equals `aff` as not runner-produced.
R5: When an acceptance names a claim id that exists in `.affidavit/manifest.json`, `orchestra close-batch` refuses transition `done` unless `aff verdict` exits 0 for that claim at the close revision.
R6: When an acceptance names a claim id that exists in `.affidavit/manifest.json`, `orchestra close-batch` refuses transition `done` unless `aff recheck` exits 0 for that claim.
R7: Orchestra skill and skill-reference text do not instruct creating a method `tdd` or `check` check-run with `runner` set to `aff`.
R8: `orchestra close-batch` does not import the `affidavit` Python package.
R9: For oracle-backed closes that need assertion-level red classification, Orchestra obtains that classification only by invoking an Affidavit CLI command.

## Acceptance criteria

- Automated tests fail a fixture check-run stamped `runner: "aff"` at close and pass an otherwise identical run stamped `runner: "orchestra"`.
- Automated tests fail close `done` for a manifest-backed acceptance when `aff verdict` or `aff recheck` would be non-zero, and pass when both succeed (mocked or fixture CLI).
- A skill/portability scanner (or equivalent test) fails text that creates a `tdd`/`check` check-run with `runner: "aff"` and passes current skills after the rewrite.
- Import-boundary test fails if `orchestra/close_batch.py` (or its call graph under `orchestra/`) imports `affidavit`.
- Oracle-backed close path invokes Affidavit CLI for assertion-level red and refuses clearly when that CLI is missing or non-zero.

## Constraints

- Workflow policy (red-first, dirty-pass, suite gates, close-batch request shape) stays in Orchestra.
- Affidavit remains the evidence tool: observation → bind → recheck, plus verdict/attest; this phase does not add a generic `aff run` for arbitrary commands.
- Prior decisions `check-run-authority` and `close-batch-store-authority` remain in force: agents do not invent pass/fail for `tdd`/`check`.

## Non-goals

- Sealing arbitrary check-runs with `aff attest`.
- Implementing Affidavit `second-runner`.
- Migrating historical dogfood check-runs in bulk (refuse at close is enough; no store rewrite required).
- Changing adaptive-artifacts record types.

## Invariants

- Gate answers for manifest claims come only through `aff` CLI verbs, never through a forgeable `runner` string.
- Orchestra may write operational check-runs; those runs are not Affidavit evidence.

## Assumptions

- Affidavit can ship (in this phase or a blocking sibling change) a CLI entry that classifies assertion-level red from a check-run payload or id without requiring Orchestra to import Affidavit.
- Acceptances that name manifest claims can be detected from acceptance payload / verify path already used by skills (claim id in manifest).
