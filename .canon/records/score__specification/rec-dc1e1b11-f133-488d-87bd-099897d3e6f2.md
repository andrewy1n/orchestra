## Requirements

R1: When Landing is present, at the start of a wave, execute-phase creates branch `task/<phase-slug>/<task-slug>` from the current `phase/<phase-slug>` tip for every task in that wave except the verification task.
R2: When Landing is present, at the start of a wave, execute-phase adds worktree `<repo>/.worktrees/<phase-slug>--<task-slug>` checked out on that task branch for every task in that wave except the verification task.
R3: The per-task commit for a non-verification task runs in that task worktree.
R4: That per-task commit stages with `git add -A` excluding `.artifacts`.
R5: verify-work for a non-verification task runs in that task worktree.
R6: A passing check-run for a non-verification task records that task's commit as its revision.
R7: At wave end, the parent merges each passing non-verification task branch into `phase/<phase-slug>`.
R8: Those wave-end merges run in task-slug order.
R9: The wave-end integration does not rebase the task branch.
R10: The parent does not merge a task branch whose check did not pass.
R11: When a merge between a task branch and the phase branch conflicts, the parent leaves that conflict unresolved.
R12: When a merge between a task branch and the phase branch conflicts, the parent opens a blocking continuity question on the effort.
R13: When a merge between a task branch and the phase branch conflicts, the parent does not start the next wave.
R14: Re-dispatch of a non-verification task reuses branch `task/<phase-slug>/<task-slug>`.
R15: Re-dispatch of a non-verification task reuses worktree `<repo>/.worktrees/<phase-slug>--<task-slug>`.
R16: Before a re-dispatch continues, the parent merges `phase/<phase-slug>` into the task branch when the task branch does not already contain the phase tip.
R17: The verification task is dispatched in `<repo>/.worktrees/<phase-slug>` on `phase/<phase-slug>`.
R18: execute-phase does not create a task branch for the verification task.
R19: execute-phase does not add a task worktree for the verification task.
R20: When Landing is absent, execute-phase does not create a `task/<phase-slug>/<task-slug>` branch.
R21: When Landing is absent, execute-phase does not add a `<repo>/.worktrees/<phase-slug>--<task-slug>` worktree.
R22: At phase close, the parent removes each task worktree `<repo>/.worktrees/<phase-slug>--<task-slug>` for that phase.
R23: At phase close, the parent deletes each `task/<phase-slug>/<task-slug>` branch that is contained in the phase branch.
R24: The assignment orientation names that task worktree as the executor's write root.
R25: The assignment orientation does not tell the executor to avoid `git add -A`.
R26: When a non-verification task has nothing to commit, execute-phase does not create an empty commit.
R27: `tests/test_task_commit.py` fails when the per-task commit path is `<repo>/.worktrees/<phase-slug>`.

## Acceptance criteria

- With Landing, a non-verification task is committed in `.worktrees/<phase-slug>--<task-slug>` on `task/<phase-slug>/<task-slug>` before verify, and the passing check-run revision is that commit.
- At wave end only passing task branches merge into the phase branch, in task-slug order, without rebasing the task branch. A failing check leaves that task branch unmerged.
- A conflict leaves markers unresolved, opens a blocking continuity question on the effort, and holds the next wave.
- Re-dispatch reuses the same task branch and worktree, merging the phase tip into the task branch first when needed.
- The verification task runs in the phase worktree and has no task branch or task worktree. A phase with no Landing creates neither.
- Phase close removes this phase's task worktrees and deletes task branches already contained in the phase branch.
- `python3 -m pytest tests/test_task_commit.py tests/test_execute_landing.py -q` passes.

## Constraints

- The parent session is the only store writer. Executors do not call `adaptive-artifacts` and do not write `.artifacts`.
- Store writes stay on the primary checkout. Task commits and the phase commit exclude `.artifacts`.
- The phase integration checkout stays `<repo>/.worktrees/<phase-slug>` on `phase/<phase-slug>` from `main`.
- Phase close still commits that phase branch, merges it into `main`, then commits the store on the primary checkout. Push only when Landing names push as a human stop.
- The per-task commit message stays conventional: `type(scope): summary`, one or two sentences, body names the task slug, and the commit happens before verify.
- Waves stay serial. Tasks in a wave stay parallel and share one executor mode.
- Retry budgets, fix tasks, and the rule that `done` work-items are never reopened stay as retry-loop left them.
- The verification task still does not edit the tree and does not commit.
- Incidental work has no Landing section, so it follows the no-Landing rule.

## Non-goals

- Path-limited `git add` on a shared worktree as the isolation mechanism.
- Task worktrees only for waves of two or more tasks.
- Verifying a task on the phase branch, or citing a post-merge phase SHA as that task's check-run revision.
- Changing the Landing section's phase branch, phase worktree path, base, or close order.
- Auto-resolving merge conflicts.
- A task worktree or task branch for the verification task.
- Task worktrees for incidental work or for a phase with no Landing section.
- A plugin release.
- Rewriting the check-runner specification. The live commit rule moves by superseding decision `task-commit-evidence`.

## Invariants

- A passing non-verification check-run SHA is a commit on that task branch. After a clean wave-end merge, that commit is reachable from `phase/<phase-slug>`.
- A check that did not pass does not add that task's commits to the phase branch.
- A task worktree is not a directory inside the phase worktree.
- The phase worktree has no task edits during the wave.
- The parent does not edit conflict markers.
- Re-dispatch does not rebase the task branch.

## Assumptions

- The verification task is the work-item that `depends_on` every other work-item in the phase. Every other task in the wave is a non-verification task.
- Tasks in one wave can be verified against the phase tip from the start of that wave, without sibling tasks' edits.
- The verification task and the phase-end suite observe the phase branch after wave-end merges.
- A task slug is unique in the phase and is a single path segment.
- `.worktrees/` stays gitignored.
- Git will not check the same branch out in two worktrees, so each task worktree needs its own branch.
