## Requirements

R1: `orchestra analyze <phase-slug>` exits 0 when no check reports an error.

R2: `orchestra analyze <phase-slug>` exits 1 when at least one check reports an error.

R3: `orchestra analyze <phase-slug>` exits 2 and writes a message to stderr when no `score:phase` record has that subject.

R4: With `--json`, stdout is one JSON object with `phase`, `stage`, and a `findings` list whose entries carry `severity`, `code`, `subject`, and `message`.

R5: The default stage is `plan`, and the `plan` stage reports no check-run finding.

R6: With `--stage close`, the checks of the `plan` stage run and the check-run checks run as well.

R7: A phase with no active `score:specification` exits 0 and the output contains the word "skipped".

R8: A requirement id in the specification payload `requirements` that is absent from the `## Requirements` section is an error with code `spec-id-not-in-body`.

R9: A requirement id in the `## Requirements` section that is absent from the specification payload `requirements` is an error with code `body-id-not-in-spec`.

R10: A specification requirement id carried by no non-withdrawn work-item of the phase is an error with code `requirement-no-work-item`.

R11: A specification requirement id named by no active acceptance of the phase is an error with code `requirement-no-acceptance`.

R12: A requirement id on a non-withdrawn work-item of the phase that the specification does not list is an error with code `work-item-unknown-requirement`.

R13: A requirement id on an active acceptance of the phase that the specification does not list is an error with code `acceptance-unknown-requirement`.

R14: A `[NEEDS CLARIFICATION` marker outside an inline code span in the specification body is an error with code `clarification-marker`.

R15: A `[NEEDS CLARIFICATION` marker outside an inline code span in the design body is an error with code `clarification-marker`.

R16: A `## Requirements` line that joins clauses with `and` or a semicolon is a warning with code `compound-requirement`, and a warning never changes the exit code.

R17: In the `close` stage, an active acceptance of the phase with no `tuner:check-run` is an error with code `acceptance-no-check-run`.

R18: In the `close` stage, an active acceptance whose latest `tuner:check-run` result is not `pass` is an error with code `acceptance-not-passing`.

R19: The settle-phase skill documents the `[NEEDS CLARIFICATION: <question>]` marker for specification and design bodies and tells the agent to resolve every marker before it ends settle-phase.

R20: The plan-phase skill tells the agent to run `orchestra analyze <phase-slug>` before plan review and to refuse plan review while it exits 1.

R21: The execute-phase skill tells the agent to run `orchestra analyze <phase-slug> --stage close` after the closing verification and before the reviewer, and to refuse to start the reviewer while it exits 1.

R22: A `[NEEDS CLARIFICATION` marker inside an inline code span (backticks) is not a finding.

## Acceptance criteria

- Against a seeded temporary store with a consistent phase, `orchestra analyze` exits 0 in both stages (R1, R6).
- Removing one work-item, one acceptance, or one specification id from the seeded store each flips the exit code to 1 with the matching finding code (R8-R13).
- A seeded marker in the specification body and in the design body each flips the exit code to 1; the same text inside backticks does not (R14, R15, R22).
- A seeded compound requirement line prints a warning and the exit code stays 0 (R16).
- In the `close` stage, an acceptance with no check-run and an acceptance with a latest `fail` check-run each exit 1; the `plan` stage on the same store exits 0 (R5, R17, R18).
- Skill-scanner tests find the required instructions in settle-phase, plan-phase, and execute-phase (R19-R21).

## Constraints

- `orchestra/score/` imports only `canon`. The analysis reads check-runs by record-type string and imports nothing from `tuner`.
- `orchestra analyze` writes no record and no file.
- Tests build temporary stores and never write the real `.canon/` store.

## Non-goals

- Engine gates in `close-batch` or the phase transition. A later phase may add them.
- Oracle-hash checks. `orchestra verify recheck` and `verify verdict` own those.
- Checks on `evaluate` or `incidental` work.
- Judging whether an acceptance tests its requirement well.
- The effort brief sections. That is phase 2.

## Invariants

- The exit code is 1 if and only if at least one finding has severity `error`.
- The same store and arguments give the same output.
- A withdrawn work-item and a superseded record are never counted.

## Assumptions

- `## Requirements` lines have the form `Rn: <text>`, one per line, as settle-phase writes them.
- A `tuner:check-run` `criterion_id` is the acceptance record id (`orchestra/conductor/check.py:208`).
- A phase has at most one active specification and one active design.
