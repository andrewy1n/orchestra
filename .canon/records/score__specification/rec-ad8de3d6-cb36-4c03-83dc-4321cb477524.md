## Requirements

R1: A manifest committed in the work repo is the authority for each claim's id, text, oracle test ids, and oracle file hashes. `aff verdict` computes its result from that manifest and from re-executing the tests. It does not read the adaptive-artifacts store. A `project:check-run` in that store, including one with `runner: aff` and `result: pass`, does not change the verdict.

R2: `aff verdict` re-executes the named claims' frozen oracle tests at `--at`, and re-executes them at `--base` in a temporary worktree. It exits 0 only when, for every named claim, the oracle file bytes at that revision match the manifest hashes, the tests fail at `--base` on an assertion, and the tests pass at `--at`. An import error, collection error, or syntax error at `--base` is not a passing red.

R3: When a claim's test ids or oracle hashes differ between the manifest at `--base` and the manifest at `--at`, the `--at` manifest must contain an amendment entry that connects those two states and whose signature verifies under the allowlist committed at `--base`. The allowlist at `--at` must be byte-identical to the allowlist at `--base`. A hash change with no amendment, a signature that does not verify, a signature under a key absent from the base allowlist, or an allowlist that changed between the two revisions fails the verdict.

R4: The behavior in R1–R3 is locked by tests that invoke the `aff verdict` CLI as a subprocess. Those tests include a `--cwd` that is a phase worktree other than the store checkout, and a case where a forged stored check-run leaves the verdict unchanged.

## Acceptance criteria

- `aff verdict` exits 0 on a tree whose manifest hashes match, whose oracle tests fail at `--base` on an assertion, and whose oracle tests pass at `--at`.
- The same command exits non-zero when oracle bytes do not match the manifest, when the base failure is not assertion-level, or when the tests fail at `--at`.
- A test-id or hash change between `--base` and `--at` exits non-zero unless a verified amendment entry covers that delta and the allowlist is unchanged.
- A forged `project:check-run` does not flip a failing verdict to pass or a passing verdict to fail.
- One subprocess test runs `aff verdict` with `--cwd` pointed at a phase worktree, with the store checkout elsewhere.

## Constraints

- The verdict is a function of the work repo and the two revisions. It does not consult adaptive-artifacts records, the dashboard, or a parent-session approval flag.
- Verification of an amendment uses the allowlist at `--base`. A key added in the `--at` revision cannot authorize an amendment in that same revision.
- This phase stays in the affidavit repo. Skills, the dashboard, and the session scripts stay where they are until `orchestration-split`.
- `evidence_kind` enforcement stays in the `evidence-kind` phase. The phase-end report stays in `phase-end-evidence`.

## Non-goals

- Moving skills, the dashboard, or session scripts to another repo.
- Enforcing `evidence_kind` against test paths.
- Hunk-revert, mutant, or differential reports.
- Rotating the allowlist. A changed allowlist fails the verdict in this phase.
- Runners other than pytest.
- A durable log sink or a mirror of the verdict into the artifact store.
- Rewiring `aff close-batch` or the skills to call `aff verdict`. The verb is the gate this phase adds; callers move in `orchestration-split`.

## Invariants

- Effective oracle hashes at a revision are the claim's hashes in that revision's manifest, and the oracle file bytes at that revision match them.
- A difference in test ids or hashes between `--base` and `--at` is covered by a chain of amendment entries whose signatures verify under the base allowlist, with each step's old state equal to the previous step's new state.
- The allowlist bytes are the same at both revisions whenever a claim's tests or hashes differ, and whenever any amendment is consulted.
- The process that re-executes the tests is the verdict. Stored runs are not an input.

## Assumptions

- Both revisions contain the manifest and the allowlist. `--base` is a commit at which the oracle tests already exist and fail on an assertion; `--at` is a descendant at which those tests pass.
- The work repo can run the frozen tests with pytest.
- OpenSSH `ssh-keygen -Y` can verify a signature against an `allowed_signers` file on the machine that runs the verdict.
- `affidavit/oracle_red.py` `is_assertion_level_failure` correctly classifies pytest output for the red at `--base`.
