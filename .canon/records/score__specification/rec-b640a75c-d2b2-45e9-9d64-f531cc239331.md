## Requirements

R1: On phase Overview, when a phase has three or more tasks, the UI shows a dependency graph laid out in columns by wave (left to right).
R2: Each graph node is a task in that phase and reflects status visually.
R3: Graph edges follow depends_on relationships among those tasks.
R4: Activating a graph node opens the task overlay for that task.
R5: A task list or wave strip remains available on Overview or Tasks so ready/running work is still scannable as a list.
R6: When a phase has two or fewer tasks, the graph is omitted.
R7: Task payloads used to build the graph include depends_on task ids sufficient to draw edges without per-task detail fetches.

## Acceptance criteria

- Unit tests build lanes and edges from a seeded task list with depends_on ids.
- UI test shows graph for ≥3 tasks and hides it for ≤2.
- Node click opens task overlay.
- `npm test` passes; API/model tests cover depends_on id enrichment when implemented in Python.
- Manual: open a multi-wave phase and confirm lanes and edges match dependencies.

## Constraints

- Prefer enriching existing snapshot/phase task JSON; keep enrichment minimal (ids + existing fields).
- Do not change Textual unless required to share TaskRow serialization (prefer web path + shared model field).
- No external graph library requirement if a small SVG/HTML layout suffices; a library is allowed only if justified in plan-phase.

## Non-goals

- Editing dependencies from the graph.
- Cross-phase edges.
- Force-directed or freeform layouts.

## Invariants

- Wave numbers still come from derived task wave.
- Overview structured chrome from `phase-overview` remains; graph is an added block.

## Assumptions

- `phase-overview` has landed or this phase includes integrating the graph into its Overview layout.
