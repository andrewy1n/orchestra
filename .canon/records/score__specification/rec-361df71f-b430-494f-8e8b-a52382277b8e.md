## Requirements

R1: `bin/aff` accepts `verdict` and rejects `check` and `close-batch`. A checkout of this repo, with no orchestra tree, no `adaptive-artifacts` on PATH, and no se-workflow store binding, still produces a verdict from the committed manifest.

R2: A test fails when any module under `affidavit/` contains the text `project:`, `SE_WORKFLOW_STORE`, `store-binding.json`, or `adaptive-artifacts`.

R3: `check.py`, `close_batch.py`, `aa.py`, `aa_resolve.py`, `policy.py`, and `affidavit.tmux` live in `~/orchestra`, with the tests that cover them. `orchestra check` and `orchestra close-batch` are the commands that write workflow records. They take the arguments `aff check` and `aff close-batch` take today.

R4: The moved close path imports `is_assertion_level_red` from `affidavit.oracle_red`. Orchestra does not import `affidavit.aa`, `affidavit.aa_resolve`, `affidavit.check`, `affidavit.policy`, or `affidavit.verdict`. A gate answer is the process exit of `aff verdict`.

R5: An orchestra skill that records a `tdd` or `check` result runs `orchestra check`. A skill that closes a work-item runs `orchestra close-batch`. A skill that judges a claim in the manifest runs `aff verdict` and treats a non-zero exit as not done.

## Acceptance criteria

- `bin/aff verdict --help` exits 0. `bin/aff check --help` and `bin/aff close-batch --help` exit non-zero.
- With `adaptive-artifacts` absent from PATH, `bin/aff verdict` still judges a claim from the committed manifest.
- The boundary test fails when a fixture module under `affidavit/` contains `project:`, `SE_WORKFLOW_STORE`, `store-binding.json`, or `adaptive-artifacts`, and passes on this repo's `affidavit/` package.
- `~/orchestra` contains the moved modules and `bin/orchestra`. `orchestra check --help` and `orchestra close-batch --help` exit 0. The moved tests pass there.
- Orchestra Python imports `affidavit.oracle_red` and does not import `affidavit.aa`, `affidavit.aa_resolve`, `affidavit.check`, `affidavit.policy`, or `affidavit.verdict`.
- Skill files call `orchestra check` and `orchestra close-batch` for those steps, and still call `aff verdict` for a manifest claim.

## Constraints

- `affidavit-product`: this phase does not add the hunk, mutant, or differential audit commands. Those are later phases.
- `store-commands-home`: the store client moves to orchestra. It does not stay here as an optional add-on.
- `evidence-kind`, `phase-end-evidence`, and `evidence-e2e` stay later phases. This phase does not enforce `evidence_kind` and does not add a phase-end report.
- `aff verdict` does not read the artifact store. A stored check-run does not change its result.
- Manual, review, and suite check-run writes stay in orchestra.
- A record is not hand-edited. Moves and rewrites go through the owning tool.

## Non-goals

- Runners other than pytest.
- An `aff` subcommand for the audit questions named in `affidavit-product`.
- An orchestra binary that still exposes `aff check` or `aff close-batch`.
- Removing orchestra's dependency on adaptive-artifacts.
- Changing the arguments of check, close-batch, or verdict.

## Invariants

- `aff verdict` is a function of the work repo and the revisions on the command.
- The assertion-level rule has one implementation, `affidavit.oracle_red`. Verdict and orchestra's close path both use it.
- The affidavit package does not import orchestra. Orchestra's store client does not import affidavit, except `affidavit.oracle_red` from the close path.
- A `tdd` or `check` result is written by `orchestra check`.

## Assumptions

- `~/affidavit` is the checkout that provides the `aff` binary. `~/orchestra` is the plugin checkout, and `orchestra` is on PATH for a skill session, beside `aff`.
- `evidence-kind`'s close refusal is implemented in orchestra, because close-batch moves there.
- The seam in `aff-orchestra-seam` is the choice made in this discussion.
