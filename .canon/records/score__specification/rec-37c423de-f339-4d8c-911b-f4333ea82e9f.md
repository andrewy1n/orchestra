## Requirements

R1: `dashboard/backend/store.py` is the only module that calls `Project.list` or `Project.get`.
R2: No module under `dashboard/backend` contains `_run(`.
R3: No module under `dashboard` imports `http.server`.
R4: `dashboard/backend/model.py` does not exist.
R5: Each of the snapshot, task, phase, and journal loaders lives in its own module with its view types.
R6: Pydantic response models define every `/api/*` response.
R7: `dashboard/web/ui/src/api-types.ts` is generated from the server's OpenAPI schema with `openapi-typescript`.
R8: A Python CI check fails when `api-types.ts` is out of date.
R9: The UI imports its API types from `api-types.ts`, and `types.ts` holds no API response shape.
R10: The dashboard tests live under `tests/dashboard/`.
R11: Each existing endpoint keeps its JSON shape for a seeded store.
R12: `uv run basedpyright` passes.

## Acceptance criteria

- R1, R2, R3, R4, R5, R10: a test checks the tree and greps the sources.
- R6, R7, R8: the sync check command passes on a clean tree and fails after a model change without regeneration.
- R9: `npm run check` and `npm run lint` pass.
- R11: a characterization test compares each endpoint's JSON to a stored fixture.
- R12: `uv run basedpyright` exits 0.

## Constraints

- The canon library (`orchestra/canon`) does not change.
- `dashboard/web/ui` stays where it is until phase `ui-structure`.
- Shared helpers go in `dashboard/backend/records.py` only when two loaders use them.

## Non-goals

- Performance changes (generation signal, record cache, slim snapshot).
- New endpoints. Phase `areas-and-ideas` adds them.
- Any UI change beyond the type import.

## Invariants

- Every endpoint keeps its response shape through the phase.
- `store.py` is the only reader of the store.

## Assumptions

- `fastapi` generates a usable OpenAPI schema from the Pydantic models.
- `openapi-typescript` handles the schema without hand edits.
- The stdlib server has no user outside this repo.
