## Problem

Git subprocess wrappers are copied across canon, conductor, tuner, the CLI, and the dashboard. Four modules each define a record-payload getter. `conductor/check.py` and `conductor/suite.py` each define `parse_failing_node_ids` and `_output_sha256`. Tuner calls `ssh-keygen` from `amendment.py`, `attestation.py`, and `human_claim.py`. The stdlib server and the FastAPI app each list the same 11 API routes.

## Approach

Each helper lives in the component that may own it (`helper-owning-component`). Git subprocesses start in `orchestra.canon.git_backend`, and the record-payload getter lives in `orchestra.canon`. Callers keep their own failure behavior. The failing-node parser and the output hash live in `orchestra.conductor.check`, and suite calls them. ssh-keygen lives in one `orchestra.tuner` module. One route table in `dashboard` feeds the stdlib server and the FastAPI app.

## Exit criteria

- Git starts in one canon module, and landing still returns `None` on git failure while `git_head` still raises.
- Suite and check share one failing-node parser and one output hash.
- Claim, amendment, and attestation verification still accept a valid signature, and `ssh-keygen` appears in one tuner module.
- Both web servers answer the same eleven API paths from one route table.
- Every acceptance passes.
