## Problem

A `project:check-run` is today a claim an agent types. Nothing in the runtime runs `acceptance.verify_command`, so pass/fail, revision, and method can be invented or malformed. Dogfood evidence: most passing check-runs carry `revision: dirty`, and free-text `result`/`method` values have gotten through. Related work (red-first, tiered verification, phase-end reviewer) needs a trustworthy runner first.

## Approach

Decide at discuss: where the runner lives, how hard it owns pass/fail for `tdd`/`check`, and which contract fields become enums versus runner-only metadata. Placeholder until that choice is recorded.

## Exit criteria

Decide at plan-phase: runner produces check-runs from exit code with revision and output digest; dirty-tree policy enforced for pass; skills and close_batch use runner-produced evidence for binary methods; contract and integration tests pass through the real entry points they name.
