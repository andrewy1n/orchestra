## Problem

After marketplace install, skills and CLIs still guess where adaptive-artifacts and the se-workflow plugin live (often `~/adaptive-artifacts` or `~/.cursor/plugins/local/se-workflow`), and verify-work still shells out to `scripts/close_batch.py` instead of a se-workflow subcommand. That breaks install-from-plugin and leaves a third CLI surface.

## Approach

Plugin-root first (decisions: plugin-root-skill-paths, aa-resolve-order, close-batch-entry). Skills resolve se-workflow via `${CLAUDE_PLUGIN_ROOT}` / `${CURSOR_PLUGIN_ROOT}` then skill-relative layout. Unify AA binary lookup (env → plugin-root/sibling → PATH) and drop `~/adaptive-artifacts` as the quiet primary fallback. Move close_batch into `se_workflow` and expose `se-workflow close-batch`; update verify-work to call it.

Session shape: **one sitting**. Executor: **inline** for every wave (skills + shared resolver + CLI are tightly coupled).

Human stops: plan review; Landing merge + store commit on primary.

Collision notes: this phase owns `skills/ensure-store.md`, `skills/verify-work/SKILL.md`, `se_workflow/`, `dashboard/artifact_store.py`, and `scripts/close_batch.py`. Do not edit adaptive-artifacts. Parallel worktrees must not touch those paths.

## Exit criteria

1. Skills and runtime helpers resolve plugin / AA paths per plugin-root-first order with no quiet `~/adaptive-artifacts` primary fallback — verified by unit tests plus grep gates on resolvers and ensure-store.
2. `se-workflow close-batch` is the documented entry; skills do not call `scripts/close_batch.py` — verified by CLI tests and skill-doc / contract consistency checks.
3. Phase Landing merge + store commit completed on primary.
