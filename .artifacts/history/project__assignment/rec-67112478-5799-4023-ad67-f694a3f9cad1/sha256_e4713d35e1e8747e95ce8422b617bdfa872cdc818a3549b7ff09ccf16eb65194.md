## Approach

Edit only `skills/execute-phase/SKILL.md`. Do not edit `skills/execute-phase/references/phase-end.md` or any file under `tests/`.

After the phase worktree exists, at the start of each wave create `task/<phase-slug>/<task-slug>` from the current `phase/<phase-slug>` tip and add `<repo>/.worktrees/<phase-slug>--<task-slug>` for every task except the verification task (the work-item that `depends_on` every other phase work-item). Dispatch that verification task in `<repo>/.worktrees/<phase-slug>` on `phase/<phase-slug>` with no task branch and no task worktree. When Landing is absent, create neither a task branch nor a task worktree.

Point the executor at the task worktree. Commit there, before verify, with `git add -A -- . ':!.artifacts'`, and skip the commit when there is nothing to commit. The commit message stays conventional and its body names the task slug. `verify-work` runs in that worktree. The passing check-run revision is that commit.

At wave end, in the phase worktree, merge passing task branches into `phase/<phase-slug>` in task-slug order with `git merge`. Do not rebase the task branch. Do not merge a branch whose check did not pass. On conflict, leave the markers, open a blocking continuity question on the effort with scope `merge:<task-slug>`, and do not start the next wave.

On re-dispatch, reuse the same task branch and worktree. Merge `phase/<phase-slug>` into the task branch when it does not already contain the phase tip.

The assignment orientation names the task worktree as the write root and does not tell the executor to avoid `git add -A`.

Keep the landing sentences these tests already require, including `code writes only under the worktree`, `store writes on the primary checkout`, `commit the phase branch`, `merge into `main``, `commit the store`, `push only when it is a human stop`, and `a missing Landing section stays in the current checkout`.

### Design / decisions (quote)

## Invariants

- The passing SHA stays a commit on the task branch and is reachable from the phase branch after a clean merge.
- A failed check does not add that task's commits to the phase branch.
- Task worktrees sit beside the phase worktree, not inside it.
- The parent does not rebase a task branch and does not edit conflict markers.
- `.artifacts` is written only on the primary checkout and is excluded from task and phase commits.

## Assumptions

- Sibling tasks in a wave do not need each other's edits to pass their own checks.
- The verification task plus the phase-end suite see the integrated phase branch.
- Task slugs are unique in the phase and safe as one path segment.
- `.worktrees/` stays gitignored.

task-worktree: Every non-verification task in a Landing wave gets branch task/<phase-slug>/<task-slug> from the phase tip at wave start and worktree <repo>/.worktrees/<phase-slug>--<task-slug>. Commit and verify run there. At wave end, passing task branches merge into the phase branch in task-slug order, without rebasing. A conflict stays unresolved, opens a blocking continuity question, and holds the next wave. Re-dispatch reuses that branch and worktree and merges the phase tip in first. The verification task stays on the phase worktree. No Landing means no task branch or task worktree. At phase close, task worktrees are removed and merged task branches are deleted.

task-commit-evidence: execute-phase requires a commit per non-verification task on branch task/<phase-slug>/<task-slug> before verify, so a passing check-run carries that SHA. The parent merges that branch into phase/<phase-slug> only after the check passes.
