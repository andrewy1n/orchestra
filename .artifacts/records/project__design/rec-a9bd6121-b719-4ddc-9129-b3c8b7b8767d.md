## Architecture

Red-first is enforced at the close gate only. `se-workflow check` continues to record red and green; `close_batch.build_batch` gains a second refusal for `method: tdd` when transitioning to `done`: each such criterion must reference a runner-produced green `check_run_id` and a runner-produced `red_check_run_id` whose fail evidence precedes that green under the ordering rule, unless the request includes a finding escape.

verify-work (parent) looks up the red check-run when assembling the close-request and copies the fields the gate needs (at least red id, result=fail, revision, optional diff_sha256, runner identity). The batch still does not create `tdd`/`check` check-runs.

Skill text in verify-work is updated to match. No validate-strict or dashboard work in this phase.

## Interfaces

Close-request criteria entry for `method: tdd` on a `done` transition (when not using the finding escape for that close):

- existing: `criterion_id`, `method`, `check_run_id`, `result` (copied from green)
- new: `red_check_run_id`, plus copied red fields required for the gate (`result` must be `fail`; `revision`; `diff_sha256` when revision is `dirty`; runner marker consistent with check-runner)

`CloseRefused` (exit 2) messages name the criterion when red is missing, not runner-produced, wrong result, or fails the ancestry/dirty rule.

Finding escape: unchanged request shape; `needs` forced to `human`; claim/body must name the missing red (documented in skill; batch may require a recognizable claim substring or rely on skill+tests — prefer documenting in skill and asserting in tests that the escape path still forces human needs).

Ancestry helper: given two SHAs and a git cwd, green is allowed if equal to red or `git merge-base --is-ancestor <red> <green>` succeeds. Dirty red: skip SHA ancestry; require non-empty `diff_sha256` on the red entry.

## Decisions

- red-first-gate-locus: close-batch-refusal (not close-plus-lint, not skill-only)
- red-first-evidence-shape: request-carried (not store-lookup)
- red-first-ordering: git-ancestry (not recorded-at-order)

## Invariants

- Pass-only `tdd` + `done` + no finding → refuse.
- Valid red→green pair or finding escape → other close rules still apply.
- `check`/`manual` entries do not require `red_check_run_id`.
- Close never invents binary pass/fail for runner methods.

## Assumptions

- Git available when both revisions are SHAs.
- verify-work can list check-runs for a criterion and pick the red to pass into the request.
- Runner-produced records remain distinguishable (e.g. `runner=se-workflow`) so hand-authored reds are refused.

## Tradeoffs

- Pure close_batch stays easy to unit-test; cost is caller-side red assembly and a git dependency for SHA pairs.
- Historical pass-only `done` items stay silent until a later lint phase.
- Finding escape can still bypass red-first; that is intentional for refactor-only / pre-existing failing tests, and surfaces under Needs you.

## Risks

- Agents omit `red_check_run_id` and overuse the finding escape — mitigate with clear CloseRefused text and skill wording.
- Dirty-red then clean-green at HEAD has no SHA ancestry link — accepted via dirty+`diff_sha256` on red only; green still follows dirty-pass policy.
- Ancestry checks against the wrong cwd/worktree — document that ancestry uses the close/verify cwd (phase worktree), same as the runner.
