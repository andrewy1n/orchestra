## Architecture

`dashboard.artifact_store` owns binding parse and `resolve`. It returns a `Target` with root, store, contract, and binding metadata. `dashboard/bin/dashboard` and `se_workflow.aa.run_aa` call the same `resolve` so the dashboard and Python CLI helpers cannot disagree. Skills document that bare `adaptive-artifacts` without `--store` may still be redirected by a personal shell function; prefer `command adaptive-artifacts` or explicit `--store` from resolve.

## Interfaces

- Binding file: `{"store":"local"|"global"}`
- Env: `SE_WORKFLOW_STORE=local|global`
- `resolve(directory) -> Target`
- `StoreBindingError` for invalid binding or bound store missing `meta.json`
- `Target.cli_args()` → `--root`, `--store`, `--contract`

## Decisions

- store-modes
- binding-layers
- se-workflow-binding

## Invariants

- One store per resolve; no fallthrough when binding is set.
- Default without binding: repo meta wins over home meta (local preferred when present).

## Assumptions

- Global store path remains `~/.artifacts/<toplevel name>`.

## Tradeoffs

- Exclusive binding can error when the preferred store is missing even if the other exists; that is intentional.
- Default flips from home-first to local-if-present so unbound repos with a repo store stop hitting empty home stores.

## Risks

- Personal shell wrappers that force `--store ~/.artifacts/$proj` still bypass skills that call `adaptive-artifacts` without going through `se_workflow.aa`; docs must call that out.
