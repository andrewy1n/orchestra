## Architecture

claim-witnesses is the foundation of the verification-direction stack. It hardens the existing close and check path only. Later phases (atomic-claims → oracle-witnesses → evidence-kind → phase-end-evidence) assume a close cannot be forged.

close-batch gains a store read before building the apply batch: for each tdd/check done entry, load check_run_id (and red_check_run_id for tdd) via adaptive-artifacts get, compare criterion_id, runner, result, and revision to the request, then run existing red-first ancestry checks using store-backed revisions. Mismatch or missing record → CloseRefused / CloseRequestError; no batch written.

aff check keeps writing check-runs; tests add a primary-store + phase-worktree layout so --cwd selects the code HEAD while the store stays on the primary checkout.

## Interfaces

- close-batch CLI: same close-request JSON shape; new refusals when store lookup fails or fields disagree. Optional explicit --store if not already discoverable (prefer existing discovery used by aff check).
- aff check CLI: --cwd continues to mean "run and pin revision here"; store root must not equal cwd when cwd is a linked worktree.
- Tests: fixtures that create a temp primary repo with .artifacts and a git worktree; invoke check/close-batch with --cwd=worktree.

## Decisions

- verification-direction-stack: brief sequential phases
- close-batch-store-authority: resolve and match store check-runs
- evidence-kind-timing: deferred to phase evidence-kind (after oracle-witnesses)
- amendment-approver: parent session (applies at oracle-witnesses; recorded now)

## Invariants

- Agent-typed pass/fail cannot close tdd/check done without a matching store check-run.
- Red and green revisions used for ancestry are the store's revisions, not unchecked copies.
- Spike scripts under spikes/ are not imported by product code.

## Assumptions

- Store records for check-runs remain queryable by id from the primary checkout during close.
- verify-work continues to pass check_run_id from aff check output; it does not hand-write check-runs for tdd/check.

## Tradeoffs

Store reads add latency and a dependency from close-batch to the store layout. That is accepted so the gate cannot be forged. Restoring tdd revision refusal without red fields may break any skill path that smuggled revision for ancestry; those paths must send red fields and rely on store revisions instead.

## Risks

- Tests that always used cwd=store will keep passing while production worktree layout stays broken if R5 fixtures are weak.
- Matching on revision alone does not prove the command output; output_sha256 is out of scope here.
- Successor phases are placeholders; their discuss sessions may revise approach without changing this foundation.
