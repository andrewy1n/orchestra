## Architecture

Retry is a parent-session loop in execute-phase and plan-phase, not a new runtime service.

1. **Re-dispatch wave.** At the start of each execute-phase dispatch cycle, list `in_progress` work-items for the current phase. For each, load the latest assessment (structured) or latest check-run (simple). If the signal is retry (`next: execute` or `result: fail`) and no executor is live for that assignment, create an assignment-amendment quoting failure evidence, increment `payload.attempts`, and re-dispatch with the same `executor` as the prior wave.

2. **Fix tasks.** When the closing verification task's check fails and the parent attributes the cause to another task's code, create a new work-item + acceptance in the same phase (kind matches the phase effort), empty `depends_on`, Approach derived from the failure. Update the verification work-item's `depends_on` to include the fix. Do not transition any `done` item. When the fix reaches `done`, `derived.ready` makes verification selectable again.

3. **Budget.** Optional work-item field `attempts` counts re-dispatches. Defaults: 2 re-dispatches per task, or cumulative executor running time ≥ 2× `estimate_minutes` when set (whichever first); 3 fix tasks created for the phase. Overrides live in the phase body's run facts (same place as other phase-run facts). On exhaustion: blocking continuity-question `scope: retry:<task-slug>`, finding `needs: human`, stop selecting that task for dispatch.

4. **next: plan.** plan-phase, when handed an assessment with `next: plan` for this phase, materializes the missing task(s) for the uncovered requirement, updates depends edges as needed, and opens/re-opens the plan-review continuity-question for the delta.

5. **Dashboard.** Task rows that have `attempts` > 0 show `attempt n/budget` using the effective per-task budget (default or run-fact override).

Evidence escalation remains the router for assessment `level` / `next`. Budget does not raise levels.

## Interfaces

- Contract: add optional `attempts` (integer) on `project:work-item`.
- execute-phase skill: retry selection before planned selection; amendment + attempts; fix-task creation; budget check; document run-fact override keys.
- plan-phase skill: handle `next: plan` assessments.
- verify-work: unchanged routing semantics; may note that parent will re-dispatch or create fix tasks.
- Dashboard model/app: render attempt/budget on retried rows.
- Tests: selection, amendment, fix-task + depends_on re-gate, budget exhaustion, no reopen of `done`, skill↔contract consistency.

Phase run-fact keys (document in skill; exact names fixed at plan-phase if needed): per-task re-dispatch cap, per-task time multiplier, per-phase fix-task cap.

## Decisions

- retry-loop-scope: full #7 (re-dispatch, fix tasks, budget, next: plan, dashboard attempts)
- retry-budget: hard budget backstop; defaults 2 re-dispatches or 2× estimate_minutes, 3 fix tasks/phase; evidence ladder unchanged for routing
- fix-task-shape: new work-item + depends_on on verification; never reopen `done`
- next-plan-consume: plan-phase adds missing tasks and re-opens plan review

## Invariants

- Single writer; executors do not call adaptive-artifacts for store writes.
- `done` is terminal for a work-item subject.
- Budget exhaustion always creates Needs you and stops dispatch for that task.
- Fix tasks and re-dispatches stay inside the current phase.

## Assumptions

- Runner check-runs expose an output tail suitable for amendment `## Correction`.
- Closing verification remains the unique work-item that depends on all other phase tasks.
- Cumulative running time can be approximated from assignment / execution-report timestamps already written (or documented as best-effort if sparse).

## Tradeoffs

- Full scope vs smaller first ship: more Landing surface now; avoids a stranded half-loop before #9/#10.
- Hard budget vs evidence-only stop: may escalate a fixable task to the user; prevents unbounded spin.
- New fix tasks vs reopen `done`: more subjects in the phase; clean lifecycle.

## Risks

- Mis-attribution when creating fix tasks (wrong sibling blamed) — mitigate with Approach quoting failing node IDs / check-run evidence; human can answer the retry question.
- Time budget hard to measure if execution-reports lack duration — fall back to re-dispatch count only when time cannot be computed; document in skill.
- Dashboard attempt display needs an effective budget number when run facts omit overrides — use defaults from skill/contract docs.
