## Architecture

Add shared phase-overlay chrome rendered for every tab: chips, progress, next-action, requirements strip, wave summary. Tab bodies use structured view models (cards/lists/sections) instead of a single markdown dump. Overview may emphasize next-action and waves; Spec/Design/Decisions wrap prose in readable sections; Tasks/Evidence/Proof use lists or matrices. Home/main left-heavy layout is explicitly out of scope this phase.

## Interfaces

- `PhaseChromeModel` (or equivalent) built once from GET /api/phase + ambient snapshot cues; reused across tabs.
- Extend `DetailViewModel` so each tab returns structured blocks, not only `{ title, body }` markdown.
- Requirements strip reads `detail.evidence` (or equivalent); clicks use `requirementHref(effort, phase, id)`.
- Wave summary groups `detail.tasks` by `wave`.

## Decisions

- `phase-overview-layout`
- `phase-overview-requirements`
- `phase-overview-home-layout-defer`

## Invariants

- Tab roles stay distinct under shared chrome.
- No JSON dump probe visible to users (sr-only probe may remain for tests).
- Home/main layout unchanged in this phase.

## Assumptions

- Next-action text can reuse snapshot position / gates phrasing already available to the client, or a short static fallback.
- Shared chrome height stays compact so tab content remains primary.

## Tradeoffs

- More chrome on every tab vs Overview-only density; empty phases need careful empty states.
- Structured Spec/Design sections may still embed markdown inside cards rather than a bespoke editor.

## Risks

- Next-action derivation may be weaker than the TUI until wired to the same rule list; acceptable to start with position text.
- Over-chrome could crowd small viewports — keep shared strip single-row where possible.
