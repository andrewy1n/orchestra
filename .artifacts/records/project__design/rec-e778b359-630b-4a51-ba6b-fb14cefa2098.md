## Architecture

atomic-claims is the second slice of the verification-direction stack. It does not change close-batch or aff check. It changes how claims are written and handed off:

1. **Plan / discuss (skills):** deliver/repair work-items always stamp atomic requirement ids; acceptances are 1:1 with those ids and carry no criterion prose; discuss splits compound requirement wording.
2. **Contract:** `criterion` becomes optional on `project:acceptance`; brief, plan, and verification acceptance roles stop requiring `criterion` and surface `requirement` / `method` / `verify_command` instead.
3. **Execute (skills):** assignment briefs quote original work-item and requirement text by id; no paraphrase of the claim.
4. **Tests:** plan-trace and skill↔contract consistency lock the skill examples and the optional/required field sets.

Oracle freeze, evidence_kind, and close refusal for thinness stay in later phases.

## Interfaces

- `contract/project-design.json`: acceptance payload/optional_payload; view role `requires_payload` for acceptance under brief, plan, verification.
- `skills/plan-phase/SKILL.md`, `skills/discuss/SKILL.md`, `skills/execute-phase/SKILL.md`, and verify-work wording as needed for "criterion" meaning.
- `tests/test_plan_trace.py`, `tests/test_skill_contract_consistency.py` (via `skill_extraction.py`).
- No new CLI flags. No adaptive-artifacts extension API.

## Decisions

- atomic-claims-enforcement: skills + contract only (not skills-only, not close-time lint)
- thin-acceptance-shape: no criterion prose; criterion optional; views drop criterion from requires_payload
- atomic-deliver-repair-ids: atomic ids required on deliver/repair; description-as-list without a spec; one acceptance per id
- original-text-briefs: briefs quote original record text by id

## Invariants

- For deliver/repair, coverage by requirement id means one acceptance naming that single id.
- Derived acceptance lines do not depend on criterion prose to render.
- claim-witnesses store-authority for check-runs remains the close gate.

## Assumptions

- Existing acceptances with fat criterion remain readable; new planning follows thin rules.
- Dashboard label polish can lag (may show requirement id when criterion is empty).
- evaluate/incidental keep today's looser requirement rules unless a later phase says otherwise.

## Tradeoffs

Skill lint without close refusal can be skipped by a non-compliant agent until a later phase adds a gate. That is accepted to keep this phase small and to avoid breaking legacy rows. Optional criterion removes a duplicate claim field at the cost of thinner UI copy until views/dashboard key off requirement text.

## Risks

- Agents may stuff multiple behaviors into one Rn wording without commas; lint must catch more than comma-splitting (plan-review still needed).
- View/dashboard tests that assert criterion strings will fail until updated.
- If plan-phase examples omit optional criterion incorrectly relative to extraction rules, skill↔contract consistency fails until examples and extractors agree.
