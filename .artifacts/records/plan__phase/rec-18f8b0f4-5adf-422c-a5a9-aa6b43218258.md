## Problem

Parallel tasks in one phase share `<repo>/.worktrees/<phase-slug>` and `phase/<phase-slug>`. Each task commits with `git add -A` (excluding `.artifacts`), so one task can commit another task's unfinished edits. The assignment orientation can warn against that. Git does not enforce the warning.

## Approach

Decisions: task-worktree, task-commit-evidence.

Each non-verification task in a Landing wave gets branch `task/<phase-slug>/<task-slug>` from the phase tip at wave start and worktree `<repo>/.worktrees/<phase-slug>--<task-slug>`. The executor commits there with `git add -A` excluding `.artifacts`, and verify-work runs there. The passing check-run cites that commit. At wave end the parent merges passing task branches into `phase/<phase-slug>` in task-slug order, without rebasing. A conflict stays unresolved, opens a blocking continuity question, and holds the next wave. Re-dispatch reuses the task branch and worktree and merges the phase tip into the task branch first. The verification task stays on the phase worktree and does not commit. Phases without Landing, and incidental work, stay in the current checkout. At phase close the parent removes this phase's task worktrees and deletes task branches already contained in the phase branch. The phase worktree, store-on-primary, and merge-to-main close stay as they are.

## Exit criteria

- `python3 -m pytest tests/test_task_commit.py -q` passes, and the skill commits a non-verification task in `.worktrees/<phase-slug>--<task-slug>` before verify.
- `python3 -m pytest tests/test_execute_landing.py tests/test_task_commit.py -q` passes. Store writes stay on the primary checkout. A phase with no Landing gets no task worktree. Phase close still merges `phase/<phase-slug>` into `main`.

## Proof

kind: commands

A human runs `python3 -m pytest tests/test_task_commit.py tests/test_execute_landing.py -q` and checks that the per-task commit path is the task worktree.
