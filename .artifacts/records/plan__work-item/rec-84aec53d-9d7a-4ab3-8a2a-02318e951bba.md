## Description

Prove the loop records and routes on a fresh store through the real CLI.

## Approach

Add `tests/test_evidence_loop.py`. Follow `tests/test_contract_self_consistency.py`: subprocess the `adaptive-artifacts` CLI against a fresh git store built from `contract/project-design.json`. Do not import the runtime.

Cover these cases:

- Happy path. Create a specification with `R1`, a design, a work-item whose `requirements` is `R1`, an acceptance whose `requirement` is `R1`, a passing check-run with `evidence_kind`, an assessment `status` `verified` `next` `release` `confidence` `high`, and a release `state` `ready`. The release payload is `ready`, not `deployed`.
- Implementation failure. A check-run `result` `fail` has no `level` and no `next`. A separate assessment has `level` `implementation` and `next` `execute`. The work-item stays `in_progress`.
- Design failure. An assessment `level` `design` `next` `design`, with no transition of the work-item to `done`. The check-run, if any, still has no `level` or `next`.
- Evidence escalation. Supersede an `implementation` / `execute` assessment with a second one for the same requirement. The skill text in `skills/verify-work/SKILL.md` says to raise to `design` when the new check-run adds no evidence kind and the cause is unchanged. The test creates that second assessment with `level` `design` and `next` `design`, and asserts the skill text. A second case adds a new `evidence_kind` and an assessment that stays `implementation` / `execute`.
- Parallel integration. An integration-report `result` `fail` is a legal record, and a later report can be `pass` only as a new record (observation, not an in-place edit of the fail).
- Insufficient evidence. An assessment `status` `insufficient` `level` `verification` `next` `verify` with `missing` naming the absent check. A passing check-run for a different kind does not force `status` `verified`.
- Simple mode. A check-run whose `result` is `pass` and that omits `requirement` and `evidence_kind` still creates. No assessment and no release are required for that store.

Assert `validate` accepts the store after each scenario.
