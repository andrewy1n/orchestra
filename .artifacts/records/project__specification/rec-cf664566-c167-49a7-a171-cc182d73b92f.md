## Requirements

R1: On the home screen, the side rail does not render individual journal entry rows.
R2: The home side rail still lists Needs you and Backlog for the selected effort as it does today.
R3: For a selected repair or evaluate effort, the side rail shows at most one journal teaser line that includes the open-item count (when known) and navigates to the journal screen.
R4: For deliver or incidental efforts, the home side rail shows no journal teaser.
R5: A hash route opens a journal screen for an effort that loads GET /api/journal for that effort.
R6: The journal screen lists open items first, then earlier items, each row showing record type and subject (or text).
R7: The journal screen provides a text filter that narrows visible rows by subject or text.
R8: Activating a journal row opens the existing record detail overlay for that id.
R9: Esc or the back control from the journal screen returns to the effort home view.

## Acceptance criteria

- UI tests cover: no journal rows on home; teaser present only for repair/evaluate; journal route renders open-then-rest order; filter hides non-matching rows; row opens record overlay.
- `npm test` in `dashboard/web/ui` passes for those cases.
- Manual: open a repair/evaluate effort if present (or seed), confirm home has no journal list and the journal screen is reachable from the teaser.

## Constraints

- Reuse GET /api/journal; no new write APIs.
- Do not change Textual in this phase.
- Do not remove Needs you or Backlog from the home rail.

## Non-goals

- Milestone navigation (prior phase).
- Deep-link parsing in markdown (phase `deep-links`).
- Changing journal record types or ordering rules in `dashboard.journal`.

## Invariants

- Journal ordering remains open then rest as `dashboard.journal.ordered`.
- Snapshot polling is unchanged.

## Assumptions

- Effort `kind` on the snapshot distinguishes repair and evaluate from deliver and incidental.
