## Requirements

R1: Every `deliver` or `repair` work-item carries one or more atomic requirement ids in `payload.requirements` (comma-separated). When no `project:specification` exists for the phase, the work-item `## Description` is the id'd list (each id names one observable behavior). `incidental` work stays exempt; `evaluate` follows campaign rules and is out of this phase's force.

R2: Each acceptance for deliver/repair names exactly one requirement id in `payload.requirement`. That id must appear on its work-item. Compound ids (commas, "and"-bundled surfaces, multiple observables under one Rn) are refused by skill lint and consistency tests.

R3: New acceptances are thin: no criterion prose. Skills write `criterion` as empty or omit it once the contract allows. Done meaning lives on the requirement text (specification `## Requirements`, or the work-item description when there is no spec), not on a re-summary field.

R4: The contract makes `criterion` optional on `project:acceptance` and drops `criterion` from the acceptance `requires_payload` of the `brief`, `plan`, and `verification` views, favoring `requirement`, `method`, and `verify_command` so derived views do not lead with empty or fat prose.

R5: `execute-phase` assignment briefs carry record ids and quote the original work-item Description/Approach and the requirement text for each linked id. They do not re-summarize the claim. Subagents receive that brief text verbatim.

R6: `tests/test_skill_contract_consistency.py` and `tests/test_plan_trace.py` (and any skill examples they extract) enforce R1–R5. No adaptive-artifacts extension change. No close-batch refusal for missing requirement or non-empty criterion in this phase.

## Acceptance criteria

- plan-phase / discuss / execute-phase skill text and examples match R1–R5; skill↔contract consistency passes.
- Creating or planning deliver/repair work with a compound requirement id, a missing requirement id, or fat criterion prose fails the plan-trace / consistency checks this phase adds or rewrites.
- Derived brief/plan/verification acceptance lines still render after criterion is optional (requirement + method + verify_command).
- close-batch and aff check behavior from claim-witnesses is unchanged by this phase.

## Constraints

- Edits stay in affidavit: `skills/`, `contract/project-design.json`, and tests. No `~/adaptive-artifacts` patch.
- `evidence_kind`, oracle author, freeze hashes, and amendment records are out of scope (later phases).
- Existing store acceptances with non-empty criterion remain valid; the new rules apply to new planning and skill examples.

## Non-goals

- Runtime close refusal for missing/compound requirement or non-empty criterion (option C deferred).
- Forcing a `project:specification` on every deliver/repair phase (two-modes simple path stays).
- Oracle-author subagent, frozen test ids/hashes, phase-end evidence report, README product reframe.
- Making `requirement` contract-required for every acceptance kind (incidental/evaluate would break).

## Invariants

- One acceptance covers exactly one atomic requirement id for deliver/repair.
- The claim text an executor sees is original record text, not a third paraphrase.
- Pass/fail recording remains store-backed check-runs from claim-witnesses; this phase does not weaken that.

## Assumptions

- claim-witnesses is done and close cannot be forged via agent-copied check-run fields.
- Dashboard may show thinner acceptance labels until it keys off requirement ids; that is acceptable for this phase.
- Owner approves requirement splits at plan review (lint flags compounds; humans settle the list).
