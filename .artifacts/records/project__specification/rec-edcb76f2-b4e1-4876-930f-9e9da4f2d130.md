## Requirements

R1: From the Needs-you list, `d` opens the item's detail screen and does not write; writes require the detail screen plus an explicit confirm.
R2: Detail shows evidence appropriate to the kind: manual check (check-run body, acceptance, revision vs HEAD); plan review (phase body including approach, tasks, Landing, run facts); finding (claim, basis, evidence/consequence).
R3: Confirm UX: Approve / Reject / Cancel for questions and plan review; Sign / Cancel for manual checks; Accept risk / Cancel for findings; one-line note required for Reject and Accept risk, optional otherwise.
R4: Approve plan review answers the continuity-question with the note recorded; Reject leaves the question open and writes a record that routes back to discuss/plan (finding `needs: human` or feedback as designed); Sign records `signed_by` and optional note; Accept risk sets `needs: none` with a resolution note.
R5: Writes use the revision of the record as displayed, not `@current`. On stale-revision error, refresh and show that the item changed since opened; no write.
R6: Plan-review items support distinct approve/reject actions (separate keys acceptable).
R7: Supersede stale active `dashboard-read-only*` constraints with one constraint describing the allowed write set: human gates only, via CLI, with a recorded decision.
R8: Contract gains any new optional payload fields needed (`answer`, `signed_note`, `resolution_note` or equivalent); README key table updated; tests cover confirm/cancel, reject with note, stale-revision refusal, and no CLI call on cancel.

## Acceptance criteria

- `d` from list opens detail; no store write without detail + confirm.
- Plan-review Approve and Reject behave as specified; Reject requires note and keeps dispatch blocked with a routing record.
- Manual sign and finding accept-risk record notes as specified.
- Displayed revision is passed as `--expected-revision`; concurrent change shows a visible message and skips the write.
- Stale `dashboard-read-only*` constraints superseded.
- Tests in dashboard gate/app suites cover confirm/cancel, reject+note, stale revision, cancel-no-CLI; README keys updated; skill↔contract consistency green if skills mention the fields.

## Constraints

- Dashboard writes only through the CLI for this allowed human-gate set.
- Does not change backlog promote/dismiss beyond existing behavior unless required for revision consistency.
- Independent of retry-loop / reviewer / tiered-verification feature work.

## Non-goals

- Retry attempt display (retry-loop)
- Tier-2 status (tiered-verification)
- Reviewer agent UX
- Restoring a fully read-only dashboard

## Invariants

- No human-gate clear without evidence view + confirm.
- Stale revision never silently overwrites a newer record.
- Reject never clears the plan-review block.

## Assumptions

- Needs-you detail screens already exist or can be extended for the three kinds.
- `needs-you-close` already established that some dashboard writes are allowed; constraints must catch up.
