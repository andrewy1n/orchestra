## Requirements

R1: `se-workflow check --acceptance <id> [--cwd <worktree>]` runs that acceptance's `verify_command` (for `method` `tdd` or `check`) and writes a `project:check-run` whose `result` is derived from the process outcome (`0` → `pass`, non-zero exit → `fail`, timeout or command-not-found → `blocked`), with `revision`, `exit_code`, `duration_s`, `output_sha256`, and `runner` populated, and with `requirement` / `evidence_kind` copied from the acceptance when present.

R2: A `pass` on a dirty tree is refused by default. With an explicit dirty override, the check-run is recorded with `revision: dirty` and a `diff_sha256`, and is flaggable (dashboard and/or `validate --strict`). A `fail` may be dirty (TDD red).

R3: Manual acceptances are not executed by the runner; they keep the human sign-off path (`signed_by`).

R4: The contract declares `check-run.result` and `check-run.method` / `acceptance.method` as enums (`pass|fail|blocked|insufficient` and `tdd|check|manual`). Creating a check-run with a free-text `result` or `method` fails validation.

R5: `skills/verify-work/SKILL.md` and `scripts/close_batch.py` (or its CLI successor) use runner-produced check-runs for `tdd`/`check`; agents write assessments, not invented pass/fail results. `tests/test_skill_contract_consistency.py` stays green.

R6: `execute-phase` requires a commit per task on the phase branch so a passing check-run can carry a real SHA.

R7: An integration test against a throwaway store shows a passing and a failing `verify_command` produce the expected check-run records through the CLI entry point.

R8: The plugin ships a `se-workflow` CLI entry point that exposes at least `check`, with a command layout ready for later subcommands (e.g. close-batch), installed the same way as other plugin bins.

## Acceptance criteria

- Invoking `se-workflow check` for a `tdd`/`check` acceptance produces a check-run whose `result` matches the exit outcome and whose runner metadata fields are set.
- Dirty `pass` is refused without override; with override it records `dirty` + `diff_sha256`.
- Timeout / missing command → `blocked`.
- Contract validation rejects illegal `result`/`method` values (covered by contract self-consistency or a dedicated test).
- verify-work and close path document/use the CLI for binary methods; skill-contract tests pass.
- execute-phase documents per-task commit; its tests cover that rule.
- Integration test for pass and fail via the CLI passes.

## Constraints

- Store writes go through `adaptive-artifacts`; the se-workflow CLI does not become a second store runtime.
- No change to `~/adaptive-artifacts` in this phase (no extension approval).
- Parent session remains the single writer of the store; the CLI is invoked by that session (or by a human) to produce check-runs.

## Non-goals

- Red-first enforcement (#6), tiered verification (#9), phase-end reviewer (#10).
- Moving `close_batch` fully onto the CLI (layout only; migration can follow).
- Dashboard UI redesign beyond flagging dirty passes if already cheap.
- Making `result` carry `level` or `next` (still assessment-owned).

## Invariants

- A check-run records what happened; an assessment records what it means.
- Manual criteria stay human-signed.
- One store writer: parent session / CLI under parent direction.

## Assumptions

- Existing `payload_enum` support in adaptive-artifacts is enough to enforce `result` and `method` without a runtime extension.
- Plugin install can put `se-workflow` on PATH the same class of way `dashboard/bin/dashboard` is exposed today (exact packaging detail settled in design/plan).
