## Requirements

R1: In detail and list surfaces that show a task id, activating the control opens the task overlay for that id when the task exists in the current snapshot.
R2: A phase subject reference navigates to the phase overlay for the selected effort (or the effort named beside the reference when present).
R3: A requirement id reference opens the requirement overlay when effort and phase context are known.
R4: A record id shaped like `rec-…` opens the record overlay.
R5: A milestone subject reference selects or expands that milestone in the Phases block when milestone-nav is present, or navigates to a phase in that milestone when only one context applies.
R6: Rendered markdown bodies linkify the same reference shapes when they appear as standalone tokens.
R7: Where a title is known from the snapshot or detail payload, the visible link label prefers title (and type when helpful) over the raw id.
R8: Unresolved references remain plain text (no broken navigation).

## Acceptance criteria

- Unit tests cover token detection and href builders for task, phase, requirement, record, and milestone shapes.
- UI tests click a linkified token and land on the expected overlay or milestone focus.
- `npm test` passes for those cases.
- Manual: open a task or needs item that cites another id and follow the link.

## Constraints

- Client-side linkify against snapshot/detail payloads; no new search API required for v1.
- Do not change Textual in this phase.
- Do not invent navigation for unknown token shapes.

## Non-goals

- Full-text search across the store.
- Editing records from links.
- Back-references index UI.

## Invariants

- Existing hash overlay routes remain the navigation targets.
- Non-link text rendering (markdown) stays safe (no raw HTML injection beyond the existing markdown pipeline).

## Assumptions

- Task ids, `rec-…` ids, phase subjects, requirement ids (e.g. `R12`), and milestone subjects are detectable with conservative patterns plus snapshot lookups.
