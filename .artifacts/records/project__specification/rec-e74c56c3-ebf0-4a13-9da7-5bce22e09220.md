## Requirements

R1: The web launcher listens only on 127.0.0.1.
R2: The web launcher reads the store chosen by the same resolution rules as the Textual launcher.
R3: GET /api/snapshot returns that store's efforts, phases, tasks, needs-you items, and backlog items produced by dashboard.model.
R4: GET /api/token returns the current dashboard.model.change_token value for that store.
R5: The page requests /api/token on an interval and requests /api/snapshot again only when the token value changes.
R6: The effort rail shows each effort's name, kind, and needs-you count.
R7: A finished effort with no Needs you items is hidden until the user asks to show finished efforts. A finished effort with Needs you items stays visible.
R8: The main pane shows the selected effort's goal.
R9: Selecting one phase limits the task rows to that phase. Selecting all phases shows every task in the effort.
R10: Status tabs Active, Running, Ready, Waiting, Done, and All limit the task rows to those states.
R11: The side column lists the selected effort's Needs you items.
R12: The side column lists the selected effort's journal in dashboard.journal.ordered order, each row showing the record type and subject.
R13: The side column lists the selected effort's open backlog items.
R14: Opening a phase shows the payload of GET /api/phase, including the tabs dashboard.model.tabs_for returns for that phase.
R15: Opening a task shows the payload of GET /api/task.
R16: Opening a requirement shows the payload of GET /api/requirement.
R17: Opening a record shows the payload of GET /api/record.
R18: Opening a Needs you item shows the payload of GET /api/needs.
R19: Opening a backlog item shows the payload of GET /api/backlog.
R20: The page asks for confirmation before it sends a store write.
R21: Approving a question calls dashboard.dismiss.dismiss_item with action approve and the revision the page is showing.
R22: Rejecting a question requires a note and calls dashboard.dismiss.dismiss_item with action reject and the revision the page is showing.
R23: Signing an unsigned check calls dashboard.dismiss.dismiss_item with action sign and the revision the page is showing.
R24: The signer on a sign is dashboard.dismiss.default_signer. The request cannot supply a different signer.
R25: Accepting a needs-human finding requires a note and calls dashboard.dismiss.dismiss_item with action accept and the revision the page is showing.
R26: A write for a loop-route, integration, or merge-branch Needs you item is rejected and leaves the store unchanged.
R27: When dismiss_item raises, the page shows the error and the store keeps the record it had.
R28: Dismissing an open backlog item calls dashboard.backlog.dismiss_item.
R29: Promoting an open backlog item calls dashboard.backlog.promote_item.
R30: When the Vite production build is present, GET / returns that Svelte app.
R31: The Vite dev server proxies /api to the FastAPI server.

## Acceptance criteria

- FastAPI TestClient tests load a seeded store and check R3, R4, R21–R29, including a stale Needs you revision and a refused kind.
- A test binds the app and asserts the listen address is 127.0.0.1.
- The launcher and the Textual launcher resolve the same store path for this repo.
- `npm run build` in the UI directory succeeds, and GET / serves that build.
- A dev-proxy test or Vite config assertion shows `/api` is forwarded to the FastAPI port.

## Constraints

- Store writes go through `dashboard.dismiss` and `dashboard.backlog`.
- The server does not enable CORS. The browser reaches the API through the Vite proxy in development and through the same origin in use.
- Styling is Tailwind in the Svelte app.
- The HTTP stack is FastAPI and uvicorn.
- `dashboard/` stays out of the installed orchestra package.
- Needs you clears pass the revision the page displayed. They do not send `@current`.

## Non-goals

- Removing the Textual dashboard, or moving tmux keys, the status line, or the bell to the browser.
- Server-sent events.
- Listening beyond 127.0.0.1, or adding a shared secret.
- A dark-theme toggle.
- Copying the terminal's agent prompt to the clipboard.
- Installing the web UI through the orchestra package or plugin.
- Store actions the terminal dashboard does not already perform.

## Invariants

- Both dashboards read `dashboard.model` for the resolved store.
- A non-human-dismissible Needs you kind cannot be cleared from the page.
- The browser cannot set `signed_by`.

## Assumptions

- The operator builds and runs this from an orchestra checkout.
- Node and npm are available where the UI is built.
- One person uses the machine. Loopback is the trust boundary.
